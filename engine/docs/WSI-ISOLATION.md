# WSI isolation

This guide defines framegen-vulkan's Vulkan-layer discovery and presentation ownership. [runtime configuration transitions](RUNTIME-TRANSITIONS.md) owns swapchain replacement and retirement.

The [maintenance checklist](../../MAINTENANCE.md) identifies upstream dependencies and review triggers. Gamescope sessions are outside this boundary by default: `fgvk` starts them without framegen-vulkan. `FGVK_GAMESCOPE=1` is an experimental opt-in that lets the launcher and the layer run in them.

## Why presentation needs one owner

The single framegen-vulkan layer owns reconstruction and every resource, so there is one resource and scheduling owner.

The legacy timing fallback for ordered SDR through a lower WSI layer uses `VK_GOOGLE_display_timing` only when the lower chain advertises it and the application has enabled neither Google nor EXT presentation timing nor the `presentWait`/`presentWait2` features. Every generated and real output then receives a separate future timestamp. WSI remains the surface/protocol owner; framegen-vulkan does not open a second Wayland connection. This Google fallback does not apply to application-owned timing or completion pacing, unavailable capabilities. framegen-vulkan drains only its own feedback namespace every 32 outputs, with a count query and at most 128 records per drain, so older WSI implementations cannot accumulate session-length timing history. Failure to read that owned feedback disables this timing path. The optional EXT timing contract described below can supersede this fallback when supported.

The WSI completion-pacing exclusion is decided from the application's device-create feature chain, without changing advertised features or wait calls. A client may wait for its real-frame present ID before producing another source frame; adding framegen-vulkan's future timestamp would feed the generated-output lead back into source production. Merely enabling a present-wait extension with its feature disabled does not exclude framegen-vulkan timing. Portable retirement tests cover both wait features behind other feature nodes, disabled features, and preservation of the application chain. Real-game qualification still needs serialized and asynchronous clients; this policy check does not establish game throughput or input latency.

## Default managed launch

Standalone `fgvk` establishes the normal boundary before `vkCreateInstance`:

```text
VK_IMPLICIT_LAYER_PATH=<private framegen-vulkan manifest directory>
VK_ADD_IMPLICIT_LAYER_PATH unset
ENABLE_FGVK=1
DISABLE_LSFG=1
DISABLE_LSFGVK=1
```

The host manifest directory is `<prefix>/share/framegen-vulkan/vulkan/implicit_layer.d`. Published host packages contain 64-bit and 32-bit framegen-vulkan manifests. A prepared Flatpak uses the matching framegen-vulkan runtime extension and bounded application overrides rather than the host launcher.

The private path prevents inherited implicit layers from joining accidentally. Known competing frame-generation layers are disabled explicitly. Layer membership cannot be repaired after Vulkan starts, so launchers, manifests, packages, and Flatpak setup all enforce the same contract.

Standalone `fgvk` applies `disable_steam_overlay` from `launcher.conf` before application startup. This Performance setting defaults to on, disables Steam overlay implicit activation, removes its explicit 32-bit/64-bit Vulkan layers, and filters exact `gameoverlayrenderer.so` basenames from colon/whitespace-separated `LD_PRELOAD` entries while preserving unrelated entries and their order. Off retains the original preload string and the existing Desktop overlay selection. The value is saved globally for `fgvk` in `launcher.conf`, outside Renderer TOML. The setting may improve smoothness but can affect Steam Input and overlay features. It does not disable the compositor or Game Mode UI. All work stays at launch; diagnostic records report the configured policy and removal count, while process identity reports loaded libraries at Vulkan initialization. Neither record proves that a later runtime has not reinjected the library. Steam Deck/Proton input, overlay, Flatpak and long-session compatibility require real-game validation.

Standalone `fgvk` applies the same MangoHud identity, architecture, and gate restrictions, staging named host manifests in a private cache only when explicitly requested. See [MangoHud launch policy](LAYER-CHAINING.md#standalone-framegen-vulkan-with-mangohud).

## Presentation and swapchain policy

The managed path uses ordered SDR presentation. It owns FIFO ordering for generated and real frames. Unknown create-chain prefixes fail before driver creation rather than mutating caller-owned data. A native create chain whose maintenance1 present-mode group includes IMMEDIATE, MAILBOX or FIFO_LATEST_READY (VKD3D-Proton creates FIFO with {FIFO, IMMEDIATE} and switches per present with in-game VSync) does not use `OrderedSdr`: the group and every per-present mode node reach the lower driver, generated outputs use the mode of their batch's real, and a group that also contains FIFO keeps the FIFO relief image.

Frame Generation normally reserves lower WSI images for the largest configured generated batch. FG-only ordered presentation also requests its established relief headroom. Surface limits remain authoritative, and an initialization or memory failure retries once with the application's original minimum.

Eligible capped Fixed profiles can prepare outputs during the existing source-cap wait, Direct transport without an output-timing owner can space outputs within that interval; Renderer-owned Google or EXT timing retains its own output clock. Native Fixed FIFO participates. Caller timing attached only to the real image does not disable spacing within an existing native Fixed cap: generated images need their own submission slots, while the real image retains its original caller target, ID and fence. Actual caller timing still excludes the learned ready-output fallback and other cap transports. An admitted native worker waits on the existing final backend timeline value and owns the complete output batch; readiness does not add a producer wait after source limiting. Readiness timeout drains retained images without timed catch-up slots. The application still returns no earlier than its original cap deadline. See [output timing within an existing base cap](ADAPTIVE-VALIDATION.md#output-timing-within-an-existing-base-cap) for automatic-cap eligibility, image-capacity and admission-pressure guards, fallback behavior, and required source/output evidence.

Fixed refresh retains the 3.3 ordered generated-image acquire, including the 50 ms application-present ceiling configured by the launcher, so ordinary FIFO image release on Steam Deck and other non-VRR devices is not misclassified as failed generated load. A shorter explicit ceiling always wins, and the boundary cannot recursively expand when framegen-vulkan's own wait reduces observed source FPS. If the lower transport still cannot supply the next image, framegen-vulkan stops that generated delivery, drains the already scheduled backend timeline, preserves the real frame, and moves following frames to zero-wait admission before backend work. Generated delivery resumes as soon as a complete batch is available, but zero-wait preflight remains armed until consecutive complete batches account for one returned-image turnover; a single available frame cannot repeatedly re-expose gameplay to the bounded wait. The turnover proof derives only from the lower image count and generated batch size, so it does not change across 60, 90, 120, or higher refresh rates. One hold therefore cannot become a long scheduler backoff or a repeated bounded stall. Headroom-tight batches remain zero-wait preflight so they cannot reserve work they cannot deliver. Fixed keeps sequential ordered delivery because its multiplier is an explicit workload selection. When the returned pool fits that Fixed batch beyond the application's minimum, no additional relief image is required; without relief, acquisition has a shared ceiling of 50 ms per application present, reduced by any shorter configured ceiling.

**Game Swapchain Images (Restart)** is the per-profile escape hatch for games that reject framegen-vulkan's normal reservation. It preserves the application's requested minimum from the first managed create and every replacement. It is off by default, process-static, and never enabled by executable or runtime heuristics. With no reserved headroom, synthetic output can be skipped when the compositor has no free image.

Changes that need a new source/presentation pair use the game-owned recreation and safe-retirement rules in [Runtime configuration transitions](RUNTIME-TRANSITIONS.md). framegen-vulkan never destroys an active application swapchain merely to apply a profile setting.

## Transport boundary and evolution

framegen-vulkan owns the Renderer graph: generated-frame planning, synchronization, recovery, and resource lifetime. The compositor remains the authority for display state such as the presentation target and focus. framegen-vulkan does not delegate framegen-vulkan's scheduling decisions to the compositor.

The current deployment path follows this ownership model: managed launches use framegen-vulkan's ordered SDR transport with one presentation owner.

If transport-specific behavior grows, keep it behind explicit internal direct and ordered-transport boundaries selected from proven startup capabilities. Scheduling must remain above those boundaries. This separation does not by itself improve quality, latency, or performance; its value is containing compatibility failures to one transport, making each path independently testable, and allowing a transport to change without rewriting layer-chain or Frame Generation policy. Do not create parallel scheduling implementations merely to name these boundaries.

## Timing capabilities across the stack

| Path | Information and pacing owner | New capability boundary |
| --- | --- | --- |
| Direct X11 or native Wayland | Driver WSI owns image release; framegen-vulkan uses its existing Fixed policy. | Advertised Vulkan timing can supply calibrated queue completion and refresh properties. Unsupported drivers retain ordinary pacing. An X11 surface without timing reads its monitor's refresh once at swapchain creation (X5, below). No persistent protocol connection is added. |
@@DROP@@ framegen-vulkan owns FIFO annotations, absolute output targets and bounded legacy readiness estimation. | Existing compositors keep their supported contract, including wrapped-margin decoding. |
Source caps, output planning and pressure recovery must be qualified across these paths. Readiness policy is transport-specific: a direct image release and a predicted refresh are not interchangeable measurements. Legacy full WSI retains its fixed batch lead and bounded feedback drain. When a surface advertises the complete `VK_EXT_present_timing` contract, framegen-vulkan can instead learn from its own calibrated queue-completion timestamps; legacy predictions are never substituted for those observations.

X11 refresh source (X5): an Xlib or XCB surface keeps owned and application timing first. When neither reports a rate, the automatic cap uses the refresh read once per swapchain creation. The query runs on a detached, layer-pinned thread that creation never waits for; until it returns, the cap stays at the existing fallback, and a stalled server holds only that thread. A libxcb and libxcb-randr query, loaded at run time, takes the active CRTC with the largest overlap with the window (the primary output's CRTC when none overlaps) and divides its mode's dot clock by its total pixels per frame, correcting for interlaced and double-scanned modes. On Xwayland, when `WAYLAND_DISPLAY` is set, the `wl_output` with the same name supplies the exact current-mode rate, because Xwayland's synthesized RandR rates can be off by about 0.1%. Both queries open and close their own connections, block on round trips on their own thread, and never use the application's display. The rate holds for the swapchain's life, so a move to another monitor keeps the old rate until the swapchain is recreated. One log record per swapchain reports `framegen-vulkan: x11 refresh: hz=… crtc=… output=… source=randr|wayland-output`, or `framegen-vulkan: x11 refresh: hz=0 reason=…`.

Wayland refresh source (X6): a native Wayland surface whose owned and application timing gave no rate takes the output refresh from its `wp_presentation` feedback, after the Vulkan sources and the X11 query. The observer described below now exists on every native Wayland surface, not only with `FGVK_PACING_PROFILE_WAYLAND=1`. Without that capture it records nothing and only feeds the refresh: it requests feedback on every 8th present until a refresh is reported, then on every 240th, and each presented event stores its refresh (0 means unknown or variable and clears the rate). The present path reads that value without a lock and adds no socket read, roundtrip, flush or commit; the dispatch stays pending-only on the observer's private queue. Cost is one observer mutex and one pending dispatch per lower present on these surfaces, plus one feedback object per 240 presents once a rate is known. Without `wp_presentation` or with a variable refresh there is no rate, as before, and the existing `uncapped auto cap refresh: hz=… source=wp-presentation` line reports the rate when one is used.

Wayland VRR refresh source (X7): under variable refresh the feedback's refresh is 0, so a surface without a rate from X6 takes the current-mode rate of the output that `sync_output` names (or of the only bound `wl_output`, which the observer binds at version 1 on its private queue, up to eight, through the existing pending dispatch). A fixed refresh never uses it, and `uncapped auto cap refresh: hz=… source=wl-output` reports the rate.

EXT timing requires advertised `VK_EXT_present_timing`, `VK_KHR_present_id2` and calibrated timestamps, enabled device features, and surface support for absolute targets, present IDs and queue-operation-end queries. framegen-vulkan never takes an application-owned timing or present-ID namespace, never duplicates caller feature nodes, and never enables presentation waits. Each eligible FIFO swapchain owns 64 feedback reservations and a monotonic ID stream. One bounded query per source batch retires complete records; full storage stops requesting new records while preserving target-only presentation. Missing commands, unsupported clocks, excessive calibration uncertainty, timing-property errors or query failure retain existing pacing. A temporary `VK_NOT_READY` property result clears stale limits and retries once on the next source batch, using only an independently known refresh clock until properties arrive. Losing the feedback transport restores the legacy preparation lead while preserving queued output deadlines; a clock change with a working transport only invalidates learned readiness. Advertised timing alone cannot take pacing ownership without a usable refresh clock, so missing refresh information retains direct source-cap output pacing. Local clocks are calibrated against the host monotonic clock at startup, on domain changes and at most once per second during use; changed clocks invalidate learned readiness without moving ordered output targets. Timing properties distinguish the effective cycle from fixed panel refresh. Only the observed queue-completion stage trains preparation lead; display predictions and application wait durations do not. No compositor installation or update is performed by framegen-vulkan.

Direct desktop MAILBOX and IMMEDIATE requests retain their application-selected present mode when frame generation is provisioned. framegen-vulkan reserves generated images without forcing FIFO. With an effective source cap, the existing `RealFramePacer` spaces complete generated/real batches inside that cap interval; Fixed uses cap × multiplier. These modes do not need a refresh-rate estimate or EXT absolute timing to use CPU submission spacing. Application-owned timing retains precedence. With an admitted native detached worker, a complete batch without usable cap slack can instead use the bounded GPU-ready source-cadence fallback described in [Fixed validation](ADAPTIVE-VALIDATION.md#output-timing-within-an-existing-base-cap); incomplete batches keep ordinary delivery, and framegen-vulkan adds no configured source cap. MAILBOX can still replace images and the compositor can still synchronize output; CPU submission spacing cannot guarantee visible delivery of every generated image or physical tearing. Native FIFO without a timing owner can use the GPU-ready fallback and bounded final-output handoff described below.

Absolute targets prefer a supported first-pixel-visible clock, then first-pixel-out, with queue-stage targets retained when neither is reported. Stage-local target and queue-completion clocks are calibrated together but retain separate offsets: the same swapchain and domain ID do not imply that different present stages share an epoch. Only the target offset converts output deadlines; each pending feedback record retains the queue offset sampled when submitted. Common monotonic or swapchain-local domains continue using one shared calibration value. This follows the [Vulkan target-stage contract](https://docs.vulkan.org/refpages/latest/refpages/source/VkPresentTimingInfoEXT.html), including its preference for a supported stage nearest visibility, without a driver-version exclusion.

When native FIFO has no admitted Vulkan/compositor timing clock, an admitted native detached worker can use the existing GPU-ready source-cadence fallback, including when a positive configured cap never binds; cap-owned output scheduling still takes precedence whenever it supplies a batch. It retains FIFO and all caller presentation metadata, adds no IDs or presentation queries, and may hand off the current batch’s trailing outputs under the native contract below. Actual caller timing nodes and an admitted output clock exclude this fallback; enabled timing/ID/wait capabilities alone do not, and no waiting pattern turns it off. Caller IDs, timing and fences stay on the final real image, while generated outputs inherit only a detached mode override. The [validation guide](ADAPTIVE-VALIDATION.md#output-timing-within-an-existing-base-cap) owns readiness, source qualification, hitch/recovery and timeout budgets. Lower driver/compositor backpressure remains ordinary blocking; neither CPU spacing nor a non-divisor output rate guarantees uniformly spaced physical frames on a fixed-refresh panel. Qualify source throughput and visible cadence against matched FG-off/on game runs before calling the fallback a game fix.

An experimental per-output `VK_KHR_present_wait2` completion gate was rejected after reducing the same externally limited source to roughly 40 FPS. The extension can complete for replaced images and does not promise a precise relationship to visible scanout; see [Khronos completion semantics](https://docs.vulkan.org/refpages/latest/refpages/source/vkWaitForPresent2KHR.html). The retained fallback uses the existing backend timeline to establish generated-image readiness and bounded CPU output deadlines, without a new wait extension, presentation IDs or busy loop. The original fallback performed all output sleeps synchronously; native 2x can now hand off the final real output as described below. This follows the readiness-before-spacing principle in [AMD's frame-generation pacing guidance](https://gpuopen.com/manuals/fsr_sdk/techniques/frame-interpolation-swap-chain/) without adopting its Windows-specific thread or busy-wait implementation.

An admitted native detached Fixed worker can overlap a complete GPU-ready output batch with the game's next CPU frame. At device creation, framegen-vulkan appends one private ordinary queue to the existing graphics family only if unused physical capacity remains, preserving the application's queue indices, priorities and flags. The worker waits on the already-submitted final backend timeline value before spacing the complete batch, so GPU-readiness waits and output-phase holds do not run after the producer's source-cap sleep. Every retained output’s binary signal is submitted before its value-owned present is handed to the existing worker. FIFO 2x–5x may retain all generated outputs and the final real image, bounded to one complete current plan of at most five existing images. Cap-owned delivery also hands off the complete batch. That worker uses only the private queue; multiple surfaces serialize its lower queue calls, without holding that lock during sleep. It copies the singleton image, swapchain, binary wait, present ID/ID2, mode and retirement fence values, retains no caller pointers, and cannot admit a second source batch. Unknown nodes, duplicate nodes, nonsingleton arrays and direct caller result arrays are rejected. Caller IDs and fences remain on the real image; completion waits retain their driver-owned result and total timeout through the handoff described below. No private ID namespace is introduced. All native presents for a managed context with a reserved private queue use that same queue from its first present: warm-up/native-only, the synchronous first generated image, retained generated/real outputs, partial/error fallback, timing-owner changes and live FG changes. The shared mutex covers each synchronous and worker lower call; only copy/render submissions remain on the original graphics queue, with already-submitted binary waits bridging readiness. Returning from a worker lower call establishes host submission, not ordering against another Vulkan queue. [Khronos guarantees presentation-request order within a particular queue](https://docs.vulkan.org/refpages/latest/refpages/source/vkQueuePresentKHR.html), so evenly spaced calls on separate queues are insufficient. Devices without a reserved private queue keep their prior queue owner. Queue idle also drains the private queue even when no worker has been created. No future host-signaled semaphore or event gates GPU progress. No wait pattern disables this ready-output fallback: a blocking wait on the latest retained real ID from the producing thread does not turn it off, and no serialized-producer latch exists. A log-only completion spiral check reports a source period that keeps growing with its completion waits (see the validation guide); it never changes pacing. Both caller wait APIs preserve the requested ID and driver completion semantics; a pending worker handoff consumes the same total timeout as the driver wait. This prevents the fallback from learning its own display-wait delay as a progressively slower source clock. Concurrent waits remain permitted under [Khronos present-wait semantics](https://docs.vulkan.org/refpages/latest/refpages/source/vkWaitForPresentKHR.html).

#### Release-point source cap

Released source arrivals can be bursty when a translation layer queues several frames. This path measures the elapsed time across eight source intervals rather than their median or individual short arrivals. The measured period spaces outputs when the source is slower than the cap; it never changes the user cap or refresh ceiling. Native 2x worker-copy batches may overlap two newer sources in the existing three-slot ring. If application acquisition finds no spare image, it polls under the shared queue lock with condition-variable sleeps of at most 250 microseconds, preserving the caller's total timeout and lower errors. It returns after acquiring one image instead of expediting every pending batch. Other handoff paths keep their existing joins.

A worker-copy batch that misses readiness, is expedited before generated delivery, or has no room for the real slot skips its unacquired generated image. Its empty submit still consumes the staged semaphore and signals the continuation and render-slot fence. Already-acquired images retain their image-return path. Once a generated copy has been presented, the trailing real keeps a full output slot even if a resource-reuse join arrives or the old batch limit expires; that join may wait for the slot. Generated-presented/skipped diagnostics are counted on completion. No extra swapchain images or source cap are introduced. These are CPU submission and ownership guarantees; driver/compositor completion and physical cadence need separate evidence.

VKD3D-Proton presents on its D3D12 direct-queue submission thread, so holding `vkQueuePresentKHR` for a framegen-vulkan cap stalls every later D3D12 submission on that queue and the game threads that wait for them. Without a present ID (in-game VSync off), VKD3D-Proton then submits one signal-only `vkQueueSubmit2` of its completion timeline on the same queue and thread, and its separate wait thread releases the game's frame-latency event after `vkWaitSemaphores` returns. framegen-vulkan intercepts `vkQueueSubmit2`, `vkQueueSubmit2KHR`, `vkWaitSemaphores` and `vkWaitSemaphoresKHR` only when the lower device exposes them. Each capped application present arms a thread-local token that only the immediately following submit on that thread and queue can claim, and only if it has no command buffers, waits or fence and exactly one non-zero signal value. An unarmed submit costs one thread-local check and a cached lower pointer; waits take the registry lock only while a token exists. A successful wait-all that covers a token sleeps until its cap deadline, bounded at 250 ms. A wait whose timeout ends first keeps the token and returns `VK_TIMEOUT`, and wait-any calls are never delayed. A context keeps holding its present until two consecutive tokens are consumed; six unconsumed tokens restore the hold. Native Fixed FIFO with an admitted output worker, no Steam menu suspension or ordered-acquire recovery, and a cap deadline at most three intervals ahead then returns the application's present without a cap wait. The worker spaces the batch from GPU readiness on the cap's output interval. Present-ID waits (in-game VSync on) and other games keep the ordinary present hold. Destroying a context retires its tokens.

A wait for a retained real-frame ID must not reach the driver before that lower present returns a non-error result. The worker owns one delivery registry entry per device and swapchain, holding up to three records in registration order (one per identified batch); both `vkWaitForPresentKHR` and `vkWaitForPresent2KHR` consult it across calling threads without acquiring the Swapchain owner or private queue mutex. A timeout-zero poll returns `VK_TIMEOUT` while that ID is retained, a finite wait spends its original budget across handoff and driver completion, and an infinite wait remains infinite. A failed lower present returns its error without waiting on an unassociated driver ID. Delivery alone never reports presentation complete: after submission, the lower wait supplies the result. Wait2 forwarding copies its outer request only to adjust the remaining timeout, preserving the caller ID, `pNext` and immutable input. The registry retains only the latest three real ID/ID2 records per live worker; an ID it never registered goes straight to the driver, and the registry is removed at worker teardown. It does not assign IDs, enable wait features or alter source-cap deadlines. The newest record notes whether the next application acquisition overlapped that wait. When the wait finishes before acquisition, the pacer consumes the worker's measured readiness/output delay once, bounded by time actually spent joining that retained ID and retains the qualified source interval instead of relearning that delay as slower game work. An acquisition before wait completion prevents this attribution, so a concurrent multi-frame producer retains its full-source median. Completion-paced source intervals never release the ready-output fallback, whatever the wait pattern: the worker's measured wait is excluded from source-work learning, and sustained slower wait-excluded work still requalifies the source cadence. A log-only completion spiral check reports the case where the learned period keeps growing with that wait (see the [validation guide](ADAPTIVE-VALIDATION.md)). This preserves the [wait2 ID association contract](https://docs.vulkan.org/refpages/latest/refpages/source/vkWaitForPresent2KHR.html).

This path requires native Fixed GPU-ready delivery, the original graphics queue and a fully copied supported chain on the final real image. Admission follows the mode sent on each present: ordinary FIFO and the unthrottled modes (IMMEDIATE, MAILBOX, FIFO_LATEST_READY) admit complete 2x–5x batches. Application/compositor timing clocks retain precedence. A detached game-owned readiness budget uses at most one learned source period, bounded at 50 ms. Ready-output deadlines run on the worker, so gameplay GPU readiness can exceed one output slot without discarding pacing or waiting for the first deadline on the producer. The retained tail spans less than one additional source period and never starts a second batch. Every exit seals the bounded batch; generated acquisition polls under the queue mutex, then seals and drains the existing tail before a blocking acquire, retaining the remaining configured timeout. Worker deadlines retain the absolute output phase through normal wake lateness. Starts more than half a slot late rebase following slots, while normal wake and lower-call durations are not added again after every interval; overdue batches cannot replay an entire slot of debt. Eligible framegen-vulkan-cap-owned batches wait for backend readiness inside the existing cap deadline, bounded at 50 ms. If preparation misses the first output slot but completes before that deadline, the output clock moves later while retaining its full interval and previous-output phase. Late GPU readiness can shift the complete batch beyond the source-return deadline, with at most one source batch retained; the worker retains that image while the application keeps its original source-cap clock. Preparation that exhausts the worker readiness budget retains ordinary semaphore-protected image returns without timed catch-up slots. Other FIFO modes, unsupported chains and devices without a spare queue retain synchronous delivery. A chain carrying one `VkPresentTimingsInfoEXT` (`swapchainCount` 1, no inner `pNext`) is copied and rebuilt on the real output with the ID and mode nodes. Successful handoff acknowledges bounded admission; the actual lower result is retained and polled at the next application acquisition. While the worker is pending, framegen-vulkan first tries a timeout-zero lower acquisition under the private queue mutex, allowing a spare image to reach the game before the output deadline. Lock contention or unavailable images retain the bounded completion-before-blocking-acquisition path; acquisition never blocks while holding the worker queue mutex. The next present drains the retained operation before reusing framegen-vulkan resources. Polls and finite acquisitions respect their original total timeout and leave application semaphore/fence/index outputs untouched on an early failure. SUBOPTIMAL accompanies a successful acquisition; terminal errors remain sticky until recreation. Already-acquired subsequent images are returned through the lower present before propagating a delayed error. Queue/device idle drain retained host work, queue idle also waits the private queue, and retirement or destruction joins the worker before destroying synchronization resources. When no spare image is available, early-acquiring applications may still pay the output slot in acquire; this is an opportunity to overlap game work rather than a guarantee of throughput for every application. A successful real-output handoff marks the preceding delivery as detached. Complete detached windows update the full-source median without releasing eight unpaced batches for small timing changes. Actual acquisition blocking contributes its consumed wait without erasing that delivery evidence. Large full-interval improvements of at least one quarter retune after two samples; smaller sustained improvements use four consecutive faster samples with the existing full-interval and wait-excluded work tests. Detached recovery updates the interval in place and keeps its complete source window, preserving output spacing even when longer jitter runs pass the acceleration threshold. An unpaced readiness miss retains the established detached episode so compensating source samples can correct an underestimated interval; a synchronous paced batch or policy reset clears it. A short source-cap miss may use the bounded ready fallback only with that actual detached-delivery history. Eight consecutive slower arrivals with no cap-paced batch release detached cap ownership, allowing a slower game limiter to replace it without another qualification gap. Synchronous delivery retains unpaced requalification.

Presentation wait semaphores use the existing first semaphore per acquired swapchain image, while inter-copy dependencies retain their sequence ring in the second semaphore. The final generated copy signals the real image's presentation wait directly; history-only, timeout and acquired-image retirement paths preserve that same owner. A timeout after a partial batch consumes its preceding inter-copy dependency before returning the real image. No extra GPU semaphore storage is added. Reacquisition, rather than advancing a frame ring, proves that a previous presentation wait has been consumed.

The CPU pacing profiler records worker lower-call timestamps when completion is joined, before starting the next source batch. Its lower-present metric includes that actual call; layer duration and phase summaries cover only synchronous work and handoff. Deferred waiting belongs to acquisition when a caller reaches acquire early. CPU captures still do not establish physical display cadence or input latency.

Qualify changes with baseline/candidate framegen-vulkan on the same compositor. Include direct and ordered controls, Fixed, at-refresh and below-refresh targets, serialized/threaded present waits, asynchronous GPU work, cold startup, VRR toggles and compositor-return transitions. Measure source cadence separately from output cadence: a serialized real-frame wait at a fractional source/output ratio can expose output-cycle quantization, and source-cap preparation never completes that wait early. Physical qualification still needs matched scenes, output completion/visible-frame evidence and latency observations; compositor timing predictions do not establish those by themselves.

The standalone Base FPS Cap is a CPU deadline limiter before frame generation; it does not require FIFO. Native MAILBOX/IMMEDIATE can spend its existing cap wait between outputs, while FIFO and compositor transports retain their own timing contracts. For isolated hitches, the opt-in [CPU pacing capture](COLLECT_DIAGNOSTICS.md#lightweight-minecraft-pacing-capture) separates source/output boundaries, cap/readiness/output waits, private phases, application acquisition and profiler publication cost. Intentional waits alone do not establish a regression, and CPU timestamps do not measure scanout. The game-limiter estimator and cap-transition rules remain owned by [Fixed validation](ADAPTIVE-VALIDATION.md#output-timing-within-an-existing-base-cap). A complete Fixed batch paced by the configured source cap establishes that cap as the output owner; brief misses cannot add GPU-ready fallback waits that perpetuate a below-cap loop. Sustained slower-work requalification and cap/policy resets release that ownership.

The real application's present ID remains on its real image. Waits retain the driver's timeout, completion and error semantics; neither an earlier generated output nor CPU submission is reported as real-image completion. Qualify this policy with serialized and concurrent application waits, asynchronous GPU work, independent compositor-completion observations. Pause qualification distinguishes bounded native-only history rebuilding from uninterrupted generated output. Require continued real-frame delivery and prompt return to the generated cadence; preserve the full recovery metrics rather than hiding the native interval in a settling phase. Successful portable tests alone do not establish these properties or throughput.

## Supported concurrency boundary

Renderer interception state currently supports one active Vulkan instance dispatch domain per process. Applications must externally synchronize each `VkQueue` as Vulkan requires. Multiple swapchains can exist in that instance, but a `VkPresentInfoKHR` batch containing more than one swapchain is rejected when any entry is managed by framegen-vulkan; shared binary waits and per-swapchain extension arrays do not yet have a safe fan-out owner.

Do not claim general multi-instance, multi-queue, or multi-swapchain-batch support until the state is instance/queue-owned and real-hardware coverage exists.

## Diagnostics and validation

Application VSync diagnostics preserve the pre-filter dynamic present mode and pass application presentation waits through unchanged. Optional KHR/KHR2 wait hooks are exposed only by the application-facing frame-generation role when the lower command exists and diagnostics are enabled. The hooks do not enable extensions or fabricate completion. A bounded per-thread accumulator reports stable-stream wait duration and result counts at most once per second. These observations are not scheduling inputs or physical scanout evidence.

### Interpreting presentation records

The initial `presentation timing initialized` record identifies optional Renderer-owned `VK_EXT_present_timing` support on a surface. `active=0` means initialization retained existing pacing; a later `presentation timing fallback` record means feedback or clock support became unavailable. Support depends on the installed driver and WSI capabilities described [above](#timing-capabilities-across-the-stack); framegen-vulkan does not update the compositor.

The private pacing capture additionally counts the timing path actually forwarded on each lower-present attempt and the spacing between consecutive framegen-vulkan Vulkan targets; see the [capture field definitions](COLLECT_DIAGNOSTICS.md#lightweight-minecraft-pacing-capture). FIFO mode, extension advertisement and a successful initialization alone do not prove that each output carried a target. Requested target intervals remain distinct from driver/compositor completion and physical visibility. These observations add no timing query or pacing-policy input.

The separate `FGVK_PACING_PROFILE_WAYLAND=1` observer applies to native Wayland surfaces, including Wine Wayland. Without that variable the same observer only feeds the refresh source (X6, above). `wayland_presentation_feedback.cpp` binds only stable `wp_presentation` version 1 and, for the VRR refresh source (X7), `wl_output` version 1 on the borrowed application display and requests feedback immediately before each actual synchronous/retained lower present. The display helper establishes the observer's private event queue before constructing its registry and synchronization callback; pending-only dispatch cannot call application/driver listeners or read the socket. The application's existing event reader supplies events. No second display, reader, roundtrip, commit, target time or Vulkan namespace is introduced. The surface entrypoint owns the observer until retirement drains and `vkDestroySurfaceKHR` stops it before lower destruction; worker batches retain only shared diagnostic state and value identities. Feedback proxies and buffered records have fixed limits. Presented timestamps/discards are compositor reports, with their own clock and reliability flags. Multiple requests may associate with one driver commit; the report marks repeated timestamp/sequence observations as ambiguous, keeps clocks/surfaces/outputs separate, and never infers image contents or physical scanout from callback receipt time. XCB self-checks do not qualify this native Wayland boundary.

`operation=application-present-wait` summarizes calls to `vkWaitForPresentKHR` and, when supported by build headers, `vkWaitForPresent2KHR`, retaining call/result/poll counts, present-ID bounds and mean/maximum blocking duration. The optional `first_failure_result`, `first_failure_present_id`, `first_failure_timeout_ns` and `first_failure_duration_ms` fields retain the first timeout/error's result, present ID, requested timeout and actual duration, so an error is not inferred from an unrelated window maximum. Successful windows omit them; older builds do not record them. Each thread emits at most one window per second for a stable device/swapchain/API stream. Switching streams drops the partial window; the final partial window is not flushed. No record means unobserved or shorter-than-window activity, not proof of no wait. Join wait records by PID and swapchain independently of the presentation thread. With the pacing profile disabled, these wrappers are bypassed entirely.

Every preset also retains Renderer failure headers with up to eight adjacent exception-detail lines folded into the same record; additional details produce `error_details_truncated=1`. The collector recognizes unprefixed libwayland protocol errors, including `#`/`@` object IDs and destroyed proxies, both directly and under Steam's `[YYYY-MM-DD HH:MM:SS]` timestamp prefix. This preserves the reported cause of a compositor disconnect without admitting ordinary Wayland traces or unrelated game output. The source must be the original session log: an older filtered report may already have discarded these details. Errors the client never read or logged cannot be recovered, and the separate compositor system journal is outside this collector's input.

### Presentation evidence

For a default managed launch, loader and Renderer evidence must agree that the render role selected a profile and backend, and ordered SDR presentation owns delivery.

A lower layer may omit the global instance-extension entrypoint or return `VK_ERROR_LAYER_NOT_PRESENT`. Either case triggers a global query through the existing Vulkan loader owner; successful layer queries and other errors retain their original handling. Optional maintenance1 retirement requires both the instance surface dependencies and the device feature. Missing dependencies, incomplete lists and other enumeration failures retain the natural presentation fallback. The query runs at instance creation, never on presentation. Commercial-game, other-driver, 32-bit, and Flatpak evidence remains separate.

Use `VK_LOADER_DEBUG=layer` only for a short reproduction because it is verbose. The pacing profile is also opt-in and can affect timing. [Collect diagnostics](COLLECT_DIAGNOSTICS.md) gives the standard collection steps.

Any discovery, ordering, present-mode, pNext, image-reservation, or transport change needs its portable launcher/package/Flatpak contracts plus applicable fgvk Gym native Vulkan, Proton, synchronization, recovery, and runtime-family evidence. Loader success or `vkcube` does not prove real-game pacing or image correctness. Record untested architectures, sandboxes, GPUs, drivers, and hardware paths explicitly.

Present-chain filtering also preserves `VkPresentTimingsInfoEXT` (`VK_EXT_present_timing`) when a newer application or Proton runtime places it before a removed maintenance1 mode override. `FilteredPresentPNextChain` in `fgvk-render/src/pnext_chain.hpp` copies the complete outer timing node and retains its caller-owned timing array, present IDs, fences, and untouched suffix. The fixed ABI layout remains recognized when framegen-vulkan is built with older Vulkan headers, with compile-time layout checks against SDKs that expose the extension. This does not disable the extension, rewrite timing values, change which output owns application-present metadata, or weaken rejection of unknown prefix structures. `pnext-chain` tests cover immutable input, interleaved removals, null timing arrays, passthrough, and unknown-node rejection.
