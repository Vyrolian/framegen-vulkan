# framegen-vulkan code map

This map identifies code owners and call boundaries. The behavior contracts remain in [Adaptive validation](ADAPTIVE-VALIDATION.md), [Runtime transitions](RUNTIME-TRANSITIONS.md), [Spatial scaling](SCALING.md), [WSI isolation](WSI-ISOLATION.md), and [Memory management](MEMORY-MANAGEMENT.md).

## Ownership from launch to present

| Concern | Owner | Boundary |
| --- | --- | --- |
| Profile parsing and defaults | `fgvk-common/src/configuration/` | Converts saved settings into validated Renderer configuration. |
| Process and Vulkan layer dispatch | `fgvk-render/src/entrypoint.cpp`, `instance.cpp` | Selects layer roles, devices, profiles, and application-owned Vulkan objects. |
| Gamescope observations | `fgvk-render/src/gamescope_hdr_feedback.cpp` and `instance.cpp` | Samples compositor state; a feedback change cannot silently become a profile edit. |
| Sustained runtime health | `fgvk-render/src/runtime_health.*`, registered by `instance.cpp` under the existing presentation-diagnostics flag | Samples bounded proc/sysfs fields and canonical atomic memory counters on a worker; no frame requests, Vulkan calls, or recovery transitions. |
| Pacing capture | `fgvk-render/src/present_diagnostics.*`, observed by the existing entrypoint and swapchain presentation owners | Opt-in fixed-size source/output/wait/phase windows, bounded individual-output traces, actual application completion waits and correlated worst intervals, independent of broad diagnostics. Writes bounded, private framegen-vulkan-only captures; no game-output capture or worker. CPU-only mode adds no GPU queries; separate `FGVK_PACING_PROFILE_GPU=1` reuses backend-owned timestamps and the existing completion fence for consume-once GPU spans. `scripts/analyze-pacing-profile.py` explains the retained CPU boundaries without inventing JVM/GPU/display attribution. |
| Native Wayland feedback capture | `fgvk-render/src/wayland_presentation_feedback.*`, with surface lifetime in `entrypoint.cpp` and immutable synchronous/worker observations in the lower-present owner | Separate opt-in `FGVK_PACING_PROFILE_WAYLAND=1` records compositor presentation/discard outcomes on the borrowed native surface. Owns bounded proxies and a private queue; consumes only already-queued events, with no display reader, game callbacks, commits or timing-policy changes. The report preserves clocks and ambiguous commit association. |
| Fixed and Adaptive decisions | `fgvk-render/src/adaptive_scheduler.*`, `presentation_policy.hpp`, and `generated_frame_plan.hpp` | Chooses generated work, output timestamps, and pacing ownership before Vulkan submission. |
| Swapchain state and transitions | `fgvk-render/src/swapchain/` | Owns the applied profile, private resources, recovery state, and game-owned swapchain boundary. |
| Spatial reconstruction | `fgvk-render/src/spatial_scaler.*` and `spatial_scaling_policy.hpp` | Chooses geometry and records private scaling work without changing scheduler evidence. |
| Model execution | `fgvk-backend/` | Owns LSFG and LS1 resources and compute work behind the Renderer context. |
| Shader effects | The optional vkBasalt layer selected by `fgvk` | Runs as a separate Vulkan layer; Renderer scaling and Frame Generation do not own its effect chain. |
| Native Steam Remote Play | `scripts/fgvk_remote_play/` and `scripts/fgvk-remote-play` | One Python owner handles Steam file safety. The packaged command is the only entry point. Existing launchers and Renderer configuration owners retain feature and live-update policy. |

Full trace additionally observes instance/device/surface/swapchain setup in `present_diagnostics.*`, called from the existing creation entrypoints. It pairs incoming and forwarded requests without mutating them or making Vulkan queries. `scripts/analyze-vulkan-setup.py` owns offline inspection/comparison; enabled setup never feeds runtime policy or establishes actual extension use. The Wayland companion keeps strict commit adjacency and separately qualifies consecutive attachment pairs across commits without a new attachment.

## Presentation files

`Swapchain` remains the sole state owner. Its presentation methods are grouped by the work they perform:

| File | Responsibility |
| --- | --- |
| `fgvk-render/src/swapchain/present.cpp` | Orchestrates one application present, including live feedback, pacing selection, and routing to real or generated delivery. |
| `fgvk-render/src/swapchain/present/admission.cpp` | Prepares the Fixed or Adaptive frame plan, checks pipeline readiness, and handles generated-image admission and recovery. |
| `fgvk-render/src/swapchain/present/generated_frames.cpp` | Submits and presents generated frames while preserving the requested, admitted, scheduled, and delivered counts. |
| `fgvk-render/src/swapchain/present/real_frames.cpp` | Presents native, scaled, and history-only real frames and records source-copy work. |
| `fgvk-render/src/swapchain/deferred_present.hpp`, `private_present_queue.hpp` | Own bounded native Fixed output-batch handoff and value snapshots, private queue reservation, one native presentation-queue owner for synchronous/retained outputs, worker-owned backend readiness within one source period (bounded at 50 ms), completion and joining, and bounded device/swapchain delivery records that hold application present waits until their real ID reaches the driver. The worker never owns or updates Swapchain state. |
| `fgvk-render/src/swapchain/release_gate.hpp` | Owns release-point source-cap pacing: one thread-local arm per capped application present, the bounded process-wide token registry recorded from the signal-only `vkQueueSubmit2` that follows that present, the delay of the application's successful `vkWaitSemaphores` for that token until the cap deadline, and per-context activation after two observed waits. Entry points live in `entrypoint.cpp`; `present.cpp` decides whether a context holds its present or releases at the wait. |
| `fgvk-render/src/swapchain/present/retirement.cpp` | Preserves upstream present fences and retires acquired images after a failed generation path. |
| `fgvk-render/src/swapchain/present_timing.hpp` | Bounds Renderer-owned Vulkan timing feedback, calibrates supported clocks, and supplies observed queue readiness to the shared ordered timeline. |
| `fgvk-render/src/swapchain/present/internal.hpp` | Shares only presentation-local diagnostics, timing, and image-barrier helpers. It owns no mutable state or policy. |

Keep new policy decisions in their existing policy or scheduler owner, and let `Swapchain::present()` consume the result. Keep live resource replacement in `swapchain/resources.cpp`, profile transitions in `swapchain/profile.cpp`, and runtime status in `swapchain/status.cpp`. A change that crosses those boundaries needs its corresponding contract test and the validation described in [Testing framegen-vulkan](../../TESTING.md).

## Deliberate large-file boundaries

`adaptive_scheduler.cpp` keeps cadence observation, workload probes, promotion, and output planning in one scheduler state owner. Its stage methods are forced inline into `planFrame()` in optimized builds. Splitting them across translation units would need the same hot-path property or measured CPU evidence. The scheduler returns a plan; it does not acquire images or own Gamescope feedback.

`entrypoint.cpp` holds the Vulkan loader entrypoints and the per-layer registries for instances, devices, surfaces, queues, swapchains, and retirement. Both compiled layer roles use that dispatch boundary. A future split must first give those registries an explicit lifetime owner and preserve lower-layer forwarding, surface provenance, and retirement under the existing WSI contracts. Splitting the file by function length while sharing anonymous global state would obscure those invariants. Keep optional vkBasalt shader configuration in the launcher and wrapper boundary; effect ordering and execution belong to that layer.

## Internal application images (F5)

For an eligible Frame Generation swapchain, the application renders into layer-owned images instead of the lower swapchain images. `vkGetSwapchainImagesKHR`, `vkAcquireNextImageKHR`, `vkAcquireNextImage2KHR` and `vkReleaseSwapchainImagesKHR`/`EXT` answer from those images without calling the lower driver. At `vkQueuePresentKHR` the entrypoint marks the private image pending and passes its descriptor to `Swapchain::present`. The real output is copied into a lower image on the presentation worker at its deadline. The worker polls for a lower image without blocking, copies the private image into it and presents that index. It never skips the output, and no expedite or join drops it. A synchronous output materializes on the presenting thread, after every older deferred batch has been joined. It acquires a lower image, copies the private image into it, and presents that index with the copy as its wait, so the copy takes over the application's wait semaphores. The real output uses presentation-wait and retirement-fence slots after the lower slots, so a generated copy into lower image `k` never shares them with it. A private image returns to the ring only after its copy has been submitted. The application keeps the real lower `VkSwapchainKHR` handle, so present IDs and waits, present timing, HDR metadata and Reflex are unchanged.

Released Fixed batches with internal application images also try one timeout-zero lower acquire and submit their generated staging copy before sleeping for the output slot. A missed early acquire keeps the existing at-deadline polling path. The worker prepares only its current output and issues its lower present before processing another output, including at higher multipliers; no additional staging images are allocated. A prepared output follows the real-output drain rule through retirement or stopping. `FGVK_INTERNAL_PREPARE=0` disables early preparation for both real and generated worker copies. The pacing summary distinguishes `generated_prepared` from `generated_at_deadline`.

`swapchain/internal_images.hpp` holds the gate and the free-image ring with no Vulkan calls. `swapchain/internal_images.cpp` owns the private images, their dedicated device-local allocations, the copy command buffers, the release timeline and the lower-acquire fences. The gate requires a non-adaptive Frame Generation profile with a deferred-present queue, no Gamescope, no spatial scaling or HDR display resize, matching extent and format, one array layer, only the present-ID, present-wait and present-timing create flags, and optimal-tiled blit support. `FGVK_INTERNAL_SWAPCHAIN=0` disables the feature for the process. Each swapchain created with a layer context logs one `framegen-vulkan: internal swapchain images:` line with its decision, and a refused swapchain names the first failing condition. A variable surface (Wayland, no fixed current extent) is accepted: its own paths are spatial scaling, Gamescope and HDR resize, which the gate refuses separately, so the line also prints `surface=variable|fixed`.

The private image count is `min(8, max(minImageCount, 3) + 2)`, where `minImageCount` is the application's minimum image count. The two extra images let the worker hold up to three pending real images in its depth-3 batch ring while the application keeps acquiring. Each image adds one device-local allocation of the application's format and extent, so added VRAM is that count times one image. Emulated acquire waits on the private ring for a finite timeout and returns `VK_NOT_READY` for a zero timeout. A private image is pending from present until its copy has been submitted. An out-of-date, surface-lost or full-screen-exclusive-loss result from the lower path is sticky, so the application must recreate the swapchain.

The emulated acquire signals the application's semaphore on the host, with no queue submit, when the release value and the last successfully submitted `tail` value are both already reached: every copy, release and generated-work submit on the private present queue also signals a `tail` timeline with the next value (`submitPrivate`; the queued acquire itself is not tailed), and both values are read as timeline counters, which never wait (F10). The signal is a temporary import of an already-signalled SYNC_FD payload, and the first failed import disables this path for the device's lifetime (`framegen-vulkan: host acquire signal disabled`). Otherwise the acquire submits on the private present queue under `mutex` and waits only the release value, so queue order runs it after every earlier private batch. A second private queue, `DeferredPresentQueue::acquireQueue`, is still created and wait-idled under its own `acquireMutex`, but no acquire submits on it. Lock order is `mutex` before `acquireMutex`, and no path takes `mutex` while holding `acquireMutex`. `vkQueueWaitIdle` on an application queue of such a device waits the present queue under `mutex` and then the acquire queue under `acquireMutex`. `vkDeviceWaitIdle` holds both locks across the lower wait. The startup line `framegen-vulkan: internal acquire queue: active=0|1 ... host_acquire=0|1` reports the second queue and whether the host path can run on the device. When a lower image is free as the worker takes an internal real (F9b), the worker acquires and copies it then, and only the present waits for the deadline; otherwise the poll runs at the deadline, and `internal_real_prepared=` and `internal_real_at_deadline=` in the pacing-profile record show the share.

If a present ends without handing its copy to the worker or submitting it synchronously, the layer submits one empty submit on the application's present queue. That submit signals a per-image binary handoff semaphore, so queue order covers any source copy already submitted there; the release-timeline signal is then submitted on the private present queue waiting that semaphore, so the release timeline is only ever signalled on one queue. The layer frees the image, makes the swapchain sticky `VK_ERROR_OUT_OF_DATE_KHR`, and returns an error or out-of-date result. The application recreates the swapchain. This recovery waits none of the application's semaphores again. Spatial scaling does not activate on an internal swapchain; a pending scaler request waits for swapchain recreation. `FGVK_PACING_PROFILE_COPY=1` and frame-content capture (`FGVK_PACING_PROFILE_CONTENT=1`) keep internal images off, with the reason `diagnostic-copy-path`.

## GPU Headroom control

`gpu_headroom.hpp` owns the bounded utilization-to-source-cap controller. `runtime_health.cpp` owns the allowlisted exact-device reader and opt-in `GpuLoadMonitor`; Root shares at most four monitors by application device accounting identity. The first enabled presentation creates the monitor; a game that leaves Headroom Off makes no Headroom monitor allocation or DRM-device query and starts no worker or polling. Live Off immediately invalidates cached utilization and parks an existing worker without recurring wakeups; it does not wait for an already-started driver read on the presentation thread. Enabled workers publish one atomic, timestamped average and back off on missing or slow reads; they never call Vulkan. Presentation consumes only the latest value and combines the resulting cap with `RealFramePacer`. Fixed output deadlines use that effective cap; Adaptive retains its scheduler and generated capacity. Smooth Cadence source-cap/FIFO handoff ownership yields while headroom limits the source. No utilization reads occur on the present thread. Runtime status publishes only state transitions, while diagnostic samples are bounded to every two seconds.

`present_diagnostics` also owns the opt-in detailed frame trace: per-source CPU records, exact application-boundary identities and bounded delayed backend-batch attribution. The backend owns its zero-based completed-batch index; `PacingProfile` maps it to a source within a resource generation, and resource replacement clears that mapping. The presentation worker copies readiness/queue-lock timestamps through its existing completion values and performs no trace file I/O. The producer publishes detailed output records when collecting completion; source and application records survive incomplete summary windows. The existing private bounded sink, report reader and optional Wayland protocol companion own retention and offline joins. See [detailed game tracing](COLLECT_DIAGNOSTICS.md#detailed-game-frame-trace).

`native_copy_profile.hpp` is the `FGVK_PACING_PROFILE_COPY=1` application-device copy timestamp owner. It records bounded queries in existing unscaled native FG source/generated commands, collects after the existing render-fence proof and retains raw device/host calibration evidence. `present_diagnostics.cpp` publishes the records through the existing private sink; the reader owns calibrated estimates and uncertainty. No result feeds pacing, and no pre-present fence query or completion wait is added.
