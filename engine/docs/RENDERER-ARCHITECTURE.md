# framegen-vulkan code map

This map identifies code owners and call boundaries. The behavior contracts remain in [WSI isolation](WSI-ISOLATION.md) for presentation and scheduling, [Runtime transitions](RUNTIME-TRANSITIONS.md) for transport recovery and live transitions, and [Memory management](MEMORY-MANAGEMENT.md).

## Ownership from launch to present

| Concern | Owner | Boundary |
| --- | --- | --- |
| Profile parsing and defaults | `fgvk-common/src/configuration/` | Converts saved settings into validated Renderer configuration. |
| Process and Vulkan layer dispatch | `fgvk-render/src/entrypoint.cpp`, `instance.cpp` | Selects devices, profiles, and application-owned Vulkan objects. |
| Pacing capture | `fgvk-render/src/present_diagnostics.*`, observed by the existing entrypoint and swapchain presentation owners | Opt-in fixed-size source/output/wait/phase windows, bounded individual-output traces, actual application completion waits and correlated worst intervals. Writes bounded, private framegen-vulkan-only captures; no game-output capture or worker. CPU-only mode adds no GPU queries; separate `FGVK_PACING_PROFILE_GPU=1` reuses backend-owned timestamps and the existing completion fence for consume-once GPU spans. `scripts/analyze-pacing-profile.py` explains the retained CPU boundaries without inventing JVM/GPU/display attribution. |
| Native Wayland feedback capture | `fgvk-render/src/wayland_presentation_feedback.*`, with surface lifetime in `entrypoint.cpp` and immutable synchronous/worker observations in the lower-present owner | Separate opt-in `FGVK_PACING_PROFILE_WAYLAND=1` records compositor presentation/discard outcomes on the borrowed native surface. Owns bounded proxies and a private queue; consumes only already-queued events, with no display reader, game callbacks, commits or timing-policy changes. The report preserves clocks and ambiguous commit association. |
| Fixed decisions | `fgvk-render/src/presentation_policy.hpp` and `generated_frame_plan.hpp` | Chooses generated work, output timestamps, and pacing ownership before Vulkan submission. |
| Swapchain state and transitions | `fgvk-render/src/swapchain/` | Owns the applied profile, private resources, recovery state, and game-owned swapchain boundary. |
| Model execution | `fgvk-backend/` | Owns LSFG resources and compute work behind the Renderer context. |

Full trace additionally observes instance/device/surface/swapchain setup in `present_diagnostics.*`, called from the existing creation entrypoints. It pairs incoming and forwarded requests without mutating them or making Vulkan queries. `scripts/analyze-vulkan-setup.py` owns offline inspection/comparison; enabled setup never feeds runtime policy or establishes actual extension use. The Wayland companion keeps strict commit adjacency and separately qualifies consecutive attachment pairs across commits without a new attachment.

## Presentation files

`Swapchain` remains the sole state owner. Its presentation methods are grouped by the work they perform:

| File | Responsibility |
| --- | --- |
| `fgvk-render/src/swapchain/present.cpp` | Orchestrates one application present, including live feedback, pacing selection, and routing to real or generated delivery. |
| `fgvk-render/src/swapchain/present/admission.cpp` | Prepares the Fixed frame plan, checks pipeline readiness, and handles generated-image admission and recovery. |
| `fgvk-render/src/swapchain/present/generated_frames.cpp` | Submits and presents generated frames while preserving the requested, admitted, scheduled, and delivered counts. |
| `fgvk-render/src/swapchain/present/real_frames.cpp` | Presents native and history-only real frames and records source-copy work. |
| `fgvk-render/src/swapchain/present_layout.cpp`, `render_pass_description.hpp` | Translates presentation layouts for private application images in explicit barriers and compatible render passes. |
| `fgvk-render/src/swapchain/deferred_present.hpp`, `private_present_queue.hpp` | Own bounded native Fixed output-batch handoff and value snapshots, private queue reservation, one native presentation-queue owner for synchronous/retained outputs, worker-owned backend readiness within one source period (bounded at 50 ms), completion and joining, and bounded device/swapchain delivery records that hold application present waits until their real ID reaches the driver. The worker never owns or updates Swapchain state. |
| `fgvk-render/src/swapchain/batch_phase.hpp` | Pure phase lock of a just-in-time released output batch (low_latency): the start of each batch after its readiness, following the batch cadence. Its state belongs to the worker in `deferred_present.hpp`. |
| `fgvk-render/src/swapchain/release_gate.hpp` | Owns release-point source-cap pacing: one thread-local arm per capped application present, the bounded process-wide token registry recorded from the signal-only `vkQueueSubmit2` that follows that present, the delay of the application's successful `vkWaitSemaphores` for that token until the cap deadline, and per-context activation after two observed waits. Also the last timeline submit of each capped present (kind LastSubmit, a DXVK-style frame end, recorded only while no semaphore or present ID token has been used) and the native acquire fallback for applications that wait on no token. Entry points live in `entrypoint.cpp`; `present.cpp` decides whether a context holds its present or releases at the wait. `fgvk-render/src/swapchain/low_latency.hpp` is the pure delay controller of the `low_latency` setting (release points move later by a delay that keeps the lead near 2 ms) and the acquire hold rule. |
| `fgvk-render/src/swapchain/present/retirement.cpp` | Preserves upstream present fences and retires acquired images after a failed generation path. |
| `fgvk-render/src/swapchain/reflex_frame_limit.hpp`, `reflex_present_attribution.hpp` | Own per-swapchain Reflex state. The frame limit forwards the game's sleep mode with the cap interval applied. Attribution keeps the game's out-of-band present markers on a frame-generation swapchain, derives each application present's Reflex ID with the [Vulkan frame attribution rules](https://docs.vulkan.org/spec/latest/chapters/VK_KHR_surface/wsi.html#low-latency2-frame-attribution), and wraps every lower present, synchronous or on the worker, in an out-of-band pair with that ID under the lock that orders the presents. |
| `fgvk-render/src/swapchain/present_timing.hpp` | Bounds Renderer-owned Vulkan timing feedback, calibrates supported clocks, and supplies observed queue readiness to the shared ordered timeline. |
| `fgvk-render/src/swapchain/present/internal.hpp` | Shares only presentation-local diagnostics, timing, and image-barrier helpers. It owns no mutable state or policy. |

Keep new policy decisions in their existing policy or scheduler owner, and let `Swapchain::present()` consume the result. Keep live resource replacement in `swapchain/resources.cpp` and profile transitions in `swapchain/profile.cpp`. Run the corresponding contract test and the relevant Renderer suites listed by `scripts/dev.sh help` for changes across those boundaries.

## Deliberate large-file boundaries

`entrypoint.cpp` holds the Vulkan loader entrypoints and the registries for instances, devices, surfaces, queues, swapchains, and retirement. A future split must first give those registries an explicit lifetime owner and preserve lower-layer forwarding, surface provenance, and retirement under the existing WSI contracts.

## Internal application images (F5)

For an eligible Frame Generation swapchain, the application renders into layer-owned images instead of the lower swapchain images. `vkGetSwapchainImagesKHR`, `vkAcquireNextImageKHR`, `vkAcquireNextImage2KHR` and `vkReleaseSwapchainImagesKHR`/`EXT` answer from those images without calling the lower driver. At `vkQueuePresentKHR` the entrypoint marks the private image pending and passes its descriptor to `Swapchain::present`. The real output is copied into a lower image on the presentation worker at its deadline. The worker polls for a lower image without blocking, copies the private image into it and presents that index. It never skips the output, and no expedite or join drops it. A synchronous output materializes on the presenting thread, after every older deferred batch has been joined. It acquires a lower image, copies the private image into it, and presents that index with the copy as its wait, so the copy takes over the application's wait semaphores. The real output uses presentation-wait and retirement-fence slots after the lower slots, so a generated copy into lower image `k` never shares them with it. A private image returns to the ring only after its copy has been submitted. The application keeps the real lower `VkSwapchainKHR` handle, so present IDs and waits and present timing are unchanged. Reflex requests keep their handle too; with frame generation on at an output cap, the minimum interval is raised to the cap's interval, and only a changed interval is sent to the driver (`swapchain/reflex_frame_limit.hpp`).

A swapchain without internal images presents real frames only, whatever the profile says. The gate result is logged as `framegen-vulkan: internal swapchain images: active=0 reason=…`, and any reason other than `frame-generation-disabled` also logs `framegen-vulkan: frame generation unavailable for this swapchain: reason=…`.

Released Fixed batches hand every generated output to the presentation worker at every multiplier (2x through 5x), and the worker copies and presents each one in order through the same path. With internal application images, each generated output also tries one timeout-zero lower acquire and submits its staging copy before sleeping for its output slot. A missed early acquire keeps the existing at-deadline polling path. The worker prepares only its current output and issues its lower present before processing another output, including at higher multipliers; each generated output has its own staging image in each render slot (see [Memory management](MEMORY-MANAGEMENT.md)). A prepared output follows the real-output drain rule through retirement or stopping. The pacing summary distinguishes `generated_prepared` from `generated_at_deadline`.

`swapchain/internal_images.hpp` holds the gate and the free-image ring with no Vulkan calls. `swapchain/internal_images.cpp` owns the private images, their dedicated device-local allocations, the copy command buffers, the release timeline and the lower-acquire fences. The gate requires a Frame Generation profile with a deferred-present queue, matching extent and format, one array layer, only the present-ID, present-wait and present-timing create flags, and optimal-tiled blit support. Each swapchain created with a layer context logs one `framegen-vulkan: internal swapchain images:` line with its decision, and a refused swapchain names the first failing condition. A variable surface (Wayland, no fixed current extent) is accepted when the lower swapchain has the application's extent.

The application uses `PRESENT_SRC_KHR` as usual. The layer maps it to `GENERAL` for private image handles in explicit transitions and uses compatible render passes with the same mapping on private framebuffer attachments. The mapping also applies to imageless framebuffer attachments selected when recording. Copies use that backing layout on the private side and `PRESENT_SRC_KHR` on the acquired lower swapchain image before display.

The private image count is `min(8, max(minImageCount, 3) + 2)`, where `minImageCount` is the application's minimum image count. A request above eight uses the native swapchain images to meet the application's minimum. The two extra images let the worker hold up to three pending real images in its depth-3 batch ring while the application keeps acquiring. Each image adds one device-local allocation of the application's format and extent, so added VRAM is that count times one image. Emulated acquire waits on the private ring for a finite timeout and returns `VK_NOT_READY` for a zero timeout. A private image is pending from present until its copy has been submitted. An out-of-date, surface-lost or full-screen-exclusive-loss result from the lower path is sticky, so the application must recreate the swapchain.

The emulated acquire signals the application's semaphore on the host, with no queue submit, when the release value and the last successfully submitted `tail` value are both already reached: every copy, release and generated-work submit on the private present queue also signals a `tail` timeline with the next value (`submitPrivate`; the queued acquire itself is not tailed), and both values are read as timeline counters, which never wait (F10). The signal is a temporary import of an already-signalled SYNC_FD payload, and the first failed import disables this path for the device's lifetime (`framegen-vulkan: host acquire signal disabled`). Otherwise the acquire submits on the private present queue under `mutex` and waits only the release value, so queue order runs it after every earlier private batch. The present queue is the only private queue, so `vkQueueWaitIdle` on an application queue of such a device waits it under `mutex`, and `vkDeviceWaitIdle` holds `mutex` across the lower wait. The startup line `framegen-vulkan: internal acquire queue: internal_prepare=0|1 acquire_tail=0|1 host_acquire=0|1` reports the internal-prepare switch, whether the tail timeline exists, and whether the host path can run on the device. When a lower image is free as the worker takes an internal real (F9b), the worker acquires and copies it then, and only the present waits for the deadline; otherwise the poll runs at the deadline, and `internal_real_prepared=` and `internal_real_at_deadline=` in the pacing-profile record show the share.

If a present ends without handing its copy to the worker or submitting it synchronously, the layer submits one empty submit on the application's present queue. That submit signals a per-image binary handoff semaphore, so queue order covers any source copy already submitted there; the release-timeline signal is then submitted on the private present queue waiting that semaphore, so the release timeline is only ever signalled on one queue. The layer frees the image, makes the swapchain sticky `VK_ERROR_OUT_OF_DATE_KHR`, and returns an error or out-of-date result. The application recreates the swapchain. This recovery waits none of the application's semaphores again.

## Colour flow

`fgvk-render/src/color_pipeline.cpp` classifies the complete format and colour-space pair, and the backend receives the resulting encoding. Real frames and generated outputs move between the swapchain and the exchange images with the same blits for every encoding; the exchange images are 8 bytes per pixel for high-precision SDR, HDR10/PQ and linear scRGB. For HDR10/PQ, the backend decodes PQ BT.2020 to linear scRGB BT.709 (80 nits per unit) in private RGBA16F working images, runs the model with its HDR constants, and encodes each generated output back to PQ before the blit into the swapchain. Linear scRGB skips both PQ stages. Under Wine on native Wayland, winewayland reports the same HDR pairs as `VK_COLOR_SPACE_PASS_THROUGH_EXT` and sets the HDR description on the surface itself; with the Wine process flag and a Wayland surface origin they take the same paths, named `wine-hdr10-pq` or `wine-scrgb-linear`. Other HDR transfer functions and unvalidated colour spaces or formats pass through.

## Diagnostic trace and copy timing

`present_diagnostics` also owns the opt-in detailed frame trace: per-source CPU records, exact application-boundary identities and bounded delayed backend-batch attribution. The backend owns its zero-based completed-batch index; `PacingProfile` maps it to a source within a resource generation, and resource replacement clears that mapping. The presentation worker copies readiness/queue-lock timestamps through its existing completion values and performs no trace file I/O. The producer publishes detailed output records when collecting completion; source and application records survive incomplete summary windows. The existing private bounded sink, report reader and optional Wayland protocol companion own retention and offline joins. See [detailed game tracing](COLLECT_DIAGNOSTICS.md#detailed-game-frame-trace).
