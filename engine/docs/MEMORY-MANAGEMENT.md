# Renderer memory management

framegen-vulkan allocates private Vulkan resources when a swapchain or processing context is constructed, reuses them during presentation, and releases them after the owning GPU work completes. Live resource changes can temporarily keep both the active and replacement contexts allocated. Frame Generation `0x` retains startup-provisioned resources for live reactivation, while disabling Frame Generation provisioning before launch omits LSFG interop and backend ownership. Once created, the layer deliberately retains its private backend Vulkan device until process exit.

This guide owns the allocation and ownership overview. [Runtime transitions](RUNTIME-TRANSITIONS.md) owns replacement decisions, [lifecycle](LIFECYCLE.md#destruction-and-retirement) owns swapchain retirement. Those policies remain authoritative for their thresholds and compatibility rules.

## Resource owners

| Resource | Owner and lifetime |
| --- | --- |
| Application device and lower WSI swapchain images | The application and Vulkan WSI own their creation/destruction contract. framegen-vulkan may defer lower-swapchain destruction under the retirement policy; these image allocations are not part of its private memory. |
| Exported real-frame and generated-output images, shared synchronization, and presentation resources | One `Swapchain` in `fgvk-render/src/swapchain/`; a private replacement may retire a subset before the game recreates its swapchain. |
| Worker staging images for generated outputs: one staging image per generated output per render slot, created on first use: (multiplier − 1) × 3 images of the swapchain extent at most | One `RenderPass` per generated output in each `RenderSlot` (`fgvk-render/src/swapchain/swapchain.hpp`), created by `recordGeneratedCopies` with its staged signal, staging copy and per-image copies, and released with the destination images when they are replaced. |
| Internal application images (F5): private application-rendered images, dedicated device-local allocations, and copy/synchronization objects | One `InternalSwapchainImages` per eligible swapchain, owned by the instance registry and released with its swapchain (see [Internal application images](RENDERER-ARCHITECTURE.md#internal-application-images-f5)); the private count is `min(8, max(minImageCount, 3) + 2)` (see [Internal application images](RENDERER-ARCHITECTURE.md#internal-application-images-f5)), and each image adds one device-local allocation. |
| Imported exchange images, model intermediates, constant buffers, and backend command resources | A backend `ContextImpl` in `fgvk-backend/src/fgvk.cpp`; closed through `backend::Instance` after its work completes, or retained for later retirement. |
| Internal model-image blocks | One `vk::ImageMemoryPool` per backend context, shared by the LSFG shader chains that explicitly request pooled images. Bound images also retain their block owner. |
| Backend Vulkan device and shader registry | The lazily constructed process-wide backend instance. The layer enables the device-retention exception described below. |
| Host containers and setup data | Their C++ owners. These are host allocations, not Vulkan device memory. Licensed model inputs and translated resources remain subject to the process-local boundary in the [Renderer README](../README.md). |

The application-facing device and private backend device can differ. Export and import connect their exchange images to the same image payload. Dedicated `OPAQUE_FD` imports require identical image creation parameters on both devices, so each exchange image uses the combined usage flags for its renderer and backend operations.

## Allocation paths

DLL inspection in `fgvk-backend/src/extraction/dll_reader.cpp` validates the complete selected resource inventory before copying payloads. The sum of copied payload sizes must fit within the validated raw PE resource region, which itself fits within the existing 1 GiB DLL file limit. Distinct IDs may share bytes only while their combined copies fit that budget; repeated or overlapping references cannot amplify a small file into an unbounded payload allocation. Budget checks use subtraction before allocation to avoid integer overflow. This is a per-parse payload bound, not a total process-memory cap: the input file buffer, resource metadata, cached archives, and translated shaders have separate lifetimes.

`fgvk-common` owns the Vulkan wrappers. `Vulkan::findMemoryTypeIndex()` selects the first compatible memory type with the requested properties: device-local for images, or host-visible and host-coherent for buffers. Selection uses the resource's Vulkan `memoryTypeBits`; it does not classify GPUs by name or treat system RAM as an interchangeable allocation target.

| Path | Allocation behavior |
| --- | --- |
| Internal image with an explicit pool | Bind a unique aligned range from a context-local block. The image retains shared ownership of that block. |
| Internal image without a pool | Allocate a separate `VkDeviceMemory` handle using the image's reported requirements and bind at offset zero. |
| Exported or imported image | Use a separate allocation with the external-memory and dedicated-image allocation structures. External images cannot use the internal pool. |
| Buffer | Allocate a separate host-visible, host-coherent memory handle, then map/copy/unmap for upload or readback. Buffers do not use the image pool. |

Allocation or binding failure propagates to the owning construction path. A successful allocation call returning a null memory handle is also rejected. The allocator does not evict another context, alias live images, or move a failed device-local request into a different storage policy.

Transfer-only images, including Native Resolution scratch images, omit image views because Vulkan does not permit them for transfer-only usage. Sampled, storage and attachment images retain their views; import/export ownership is unchanged.

### Internal image pooling

`ImageMemoryPool` reduces separate Vulkan allocation calls for the many LSFG model intermediates. Each block has one memory type and a linear cursor. Binding searches existing blocks of the selected type, aligns the cursor to the image requirement, and reserves a non-overlapping range. The cursor rejects invalid alignment, arithmetic overflow, and requests that do not fit without changing its position.

The default minimum block size is 4 MiB. With that default, a request up to 8 MiB gets a new block sized to the larger of 4 MiB or four times its requirement. Requests above 8 MiB through 32 MiB get a 32 MiB block; a single image larger than 32 MiB gets a block sized to its own requirement. The final block size is aligned to the image requirement. These are block-sizing rules, not a total context or device-memory cap.

There is no free-list, compaction, or individual range reuse. Destroying an image does not rewind the cursor. A failed Vulkan bind after range reservation also leaves that range consumed until the block is released. The pool retains its blocks, and each successfully bound image retains its block independently; a block is freed only when the pool and all image references to it are gone. This favors context-wide construction and retirement rather than repeated individual image allocation/deallocation.

Pooling is opt-in, not a global allocator for all Renderer images. The LSFG shader chains use the context pool, while exchange images, host-visible buffers, and other images constructed without a pool keep their separate allocations. Pooling reduces allocation count; it does not reduce image dimensions or alias model intermediates. Unused block capacity and alignment padding remain allocated.

### Model scratch lifetimes

The shared 4×4 black image supplies zero prior motion to the first refinement stages. Context initialization explicitly clears it once and makes the transfer writes visible to compute sampling before the context can run. A layout transition from `UNDEFINED` does not initialize pixels; allocating new device memory must never substitute for the clear. Other model intermediates are written by their owning passes before use.

The model graph reuses existing same-format, same-extent images only after their earlier contents have reached their last reader. Beta1 borrows the first two Alpha0 outputs at the finest pyramid level after Alpha1 consumes them; after Beta1's first dispatch consumes Beta0, the next dispatch reuses Beta0's outputs as its second scratch bank. Both banks remain owned and initialized by Alpha0/Beta0. Gamma1 then borrows Alpha0's output images after the prepass. Delta1 already borrows Gamma1's second scratch set; after its first dispatch consumes Gamma0's outputs, it also reuses those outputs and the unused tail of Gamma1's first scratch set. Gamma1's first `m` images remain intact until Delta1's second half consumes them. `helpers/delta_scratch.hpp` owns that split for both model sizes and rejects incomplete or overlapping input sets.

Generated outputs in one context execute sequentially on the same compute queue and share one set of Gamma0, Gamma1 and Delta1 intermediate images at each pyramid level. The first output allocates those images; later outputs retain shared ownership, so pass-vector relocation and partial construction cannot invalidate their image references. Only the first output contributes these shared images to initialization. Output destinations, descriptor sets and timestamp buffers remain distinct for every generated output. A lower requested output count does not allocate new scratch, and a replacement context owns an independent set.

These are sequential uses of the same `VkImage`, not overlapping bindings of different images to the same memory range. For a single generated output, an explicit memory dependency orders generation after preprocessing in the same submission. Multiple outputs retain the prepass semaphore and their independent completion signals; compute dependencies order scratch reads/writes within and across passes. The context completion fence keeps the next prepass and resource retirement behind all generated work. Those dependencies must remain intact if recording, submission or concurrency changes; concurrent generated passes would require independent scratch. Temporal quality and synchronization validation must cover changing output counts, history-only steps and repeated source/history phases.

### Independent compute dispatches

The prepass records the seven Alpha pyramid levels by stage: each of Alpha0's three stages and Alpha1's history update has one combined image dependency followed by seven independent dispatches. This retains all 28 dispatches and their original shader inputs, outputs and extents, while reducing those stages from 28 compute barriers to four. Delta0's two independent preparation dispatches also share one dependency.

Delta1 can run its two four-stage branches together by borrowing the next coarser Alpha0 level's dead half-resolution temporary banks for the second branch. Those RGBA8 banks already exist in the context; no images or memory blocks are added. The constructor requires the exact count and extent, disjoint banks and no overlap with live refinement inputs or outputs. Odd pyramid rounding or an incompatible bank retains the original serial branch and scratch layout. The first branch still preserves Gamma1's live prefix. Each paired stage retains a combined image dependency before its two dispatches.

`helpers/independent_dispatch.hpp` rejects a grouped recording when any dispatch writes an image accessed by another dispatch. Shared read-only images are allowed; image-layout and queue-ownership transitions are not grouped. The checks and barrier collection occur only when creating the six cached command phases, with no additional steady-frame allocation. These are independent dispatches within one generated output; generated outputs still execute sequentially, and the preprocessing dependency, output timeline and completion fence protect scratch reuse and the next frame. Validation must include changing output counts, history-only work, odd dimensions, both model sizes.

### Recorded model commands

Each context lazily records its prepass and generated-output commands for each combined source/history phase. `helpers/temporal_phases.hpp` owns Alpha1's history counts and derives the six-phase recording period from those counts and the two source-image slots. All missing generated recordings are completed before the prepass is submitted, so a cold-cache allocation or recording failure cannot leave partial GPU work behind. The previous completed fence stays intact during recording; immediately before the first submission it is reset and the context is marked as submitted, preserving retirement protection if a later submission fails. Reuse preserves shaders, descriptors, dispatches, barriers, timeline values and completion-fence placement. Timestamp changes still update each output's uniform buffer only after previous work completes; they do not change recorded descriptor bindings. Context replacement creates a new recording set, and retirement retains old commands with their images until work completes. Retaining recordings trades a small driver command-memory allocation for lower CPU recording cost; image reuse and command-memory costs must be measured together.

When exactly one output is requested, preprocessing, a cached dependency command and generation share one `VkSubmitInfo`. The dependency uses an all-commands memory barrier covering preprocessing compute writes and blits. The context records this small dependency once, independently of its six phase recordings, and uses a fixed local command-handle array at submission. Multiple outputs retain separate submissions waiting on the prepass semaphore, allowing the driver to preserve their existing overlap and per-output completion signals; chaining each output behind the previous completion would serialize more work. History-only work retains its fenced prepass without a generated-output signal. The single-output optimization applies to both models and precisions, independently of Gamescope and presentation mode.

Pacing GPU profiling (`FGVK_PACING_PROFILE_GPU=1`) enables a query pool only on a fresh unscheduled backend context. Its queries are recorded into the same cached preprocessing, output and source-release commands; the existing timeline values, submissions, image ownership and completion fence remain intact. The query owner outlives those command recordings. The backend establishes GPU completion through its normal output wait before retrieving results; profile reads add no fence wait or blocking query-result flag and reject unavailable results. Ordinary contexts allocate no pool and perform no profiling clock reads. [Detailed game frame trace](COLLECT_DIAGNOSTICS.md#detailed-game-frame-trace) defines the diagnostic measurement boundary.

## Ownership and cleanup

The wrappers use C++ ownership to release Vulkan handles. `vk::Image` declares memory before image and image-view members so normal destruction releases the view, then the image, then its allocation or pooled-block reference. `vk::Buffer` similarly releases the buffer before its memory. `ls::owned_ptr` supplies the move-only handle owner and custom deleter; it is not a GPU-completion mechanism. The owning Vulkan device must outlive every wrapper that calls its destruction functions.

`vk::Shader` releases its input shader module after compute-pipeline creation succeeds. The compiled pipeline, layouts and model registry remain available for context reuse and live mode changes. Vulkan explicitly permits [destroying shader modules while their pipelines remain in use](https://docs.vulkan.org/refpages/latest/refpages/source/vkDestroyShaderModule.html); failure during construction still unwinds through the same handle owners.

For native FP16 Quality on AMD RADV, five four-output convolutions can use two write-disjoint pipelines. `extraction/spirv_output_split.*` accepts only a straight-line, read-only-input graph with exactly one write to each required output; unfamiliar instructions, descriptor layouts, mutable memory, storage-image reads and subgroup-dependent inputs retain the original shader. Each variant removes only the other output pair's writes and unused handle loads, allowing the driver to eliminate dead arithmetic and reduce register pressure without changing model weights, precision or Flow Scale. Preparation stays in memory at registry creation; no licensed payload is persisted. The extra compiled pipelines share the original layouts and use the existing disjoint scratch banks, compute dependencies and cached command phases, with no new images, queue submissions or steady-frame allocation. Other drivers, FP32, Performance and translated models use the original path. Changes require paired capacity/GPU-time evidence plus byte comparisons, temporal quality and synchronization validation; compiler and hardware gains are not universal.

`Swapchain::FrameGenerationResources` keeps source images, destination images, and the shared semaphore together with the backend-context owner. Its declaration order closes the context before releasing the exported resources it imports. Live handoff first establishes that the old backend and application-device work are idle, then moves the whole resource group. Preserve this order when adding members or changing replacement code.

Presentation binary waits reuse the existing semaphore storage by acquired image index; the second semaphore in each slot remains an inter-copy sequence dependency and is never presented. Reacquisition proves that the corresponding presentation wait has finished before that semaphore is signaled again. History-only, timeout and acquired-image retirement paths follow the same image ownership. Native Fixed may retain one complete ready batch for its bounded private-queue worker (up to four generated images and the existing real image at FIFO 5x), including cap-owned delivery; that worker is joined before any semaphore, fence, image or context can be destroyed, and adds no GPU image or semaphore allocation. A worker adds one shared CPU delivery record and, after receiving a caller ID, one device/swapchain registry entry for cross-thread completion waits. Storage is bounded by live workers, retains no caller pointers, and is unregistered after worker join; waiters retain the record only for their current call. See the [WSI handoff contract](WSI-ISOLATION.md).

Opt-in pacing capture buffers at most 512 individual CPU output observations per context/window, reports omissions explicitly and publishes with the existing one-second summary. The worker retains at most one copy-fence result/timestamp per bounded output call; completion joins transfer those values to the context owner. GPU mode only borrows the existing render-copy fence until worker join and never resets or destroys it. CPU-only/default operation adds no GPU query, fence observation or GPU allocation for this trace. The capture retains its existing 16 MiB file bound.

The separate native Wayland presentation observer is allocated only with `FGVK_PACING_PROFILE_WAYLAND=1`. Each observed surface owns a private client event queue, registry/presentation/discovery proxies, at most 256 outstanding feedback proxies and 512 buffered records. Its private file preserves the beginning up to 512 MiB and stops with a limit marker instead of overwriting earlier comparison phases; the file lives under `${TMPDIR:-/tmp}`, often RAM-backed, so a full capture can hold up to 512 MiB of memory; the CPU/GPU-only ring remains 16 MiB. Surface destruction first drains retained presents, then stops the observer before forwarding destruction; stop destroys only its own proxies/queue and records outstanding feedback as abandoned. Captured batches retain shared diagnostic state without borrowing mutable Swapchain state. Default and CPU/GPU-only profiling allocate none of these Wayland observation resources. Missing callbacks exhaust the bounded capacity and report unavailable evidence instead of growing a history or starting another reader.

External file descriptors have a separate ownership transition. Export returns an owned descriptor only after image-view construction succeeds. The backend context call consumes the whole descriptor batch on entry; unattempted imports remain scoped for cleanup if construction fails. Successful Vulkan import transfers descriptor ownership to Vulkan, so a later bind or view failure must not close that descriptor number again. The detailed failure contract and tests are in [external descriptor ownership](RUNTIME-TRANSITIONS.md#external-descriptor-ownership-during-resource-construction).

Shared image contents also cross Vulkan instance ownership. `fgvk-common/vulkan/external_image.hpp` owns the `GENERAL` layout boundary and `VK_QUEUE_FAMILY_EXTERNAL` release/acquire barriers. Renderer and CLI source uploads release their writes before signalling the shared timeline; the backend acquires both source slots and releases them after the generated batch or history-only work. Each generated output is released before its timeline signal and acquired by the consumer before readback, blitting or post-generation scaling. Full source uploads and output generation discard prior contents with `UNDEFINED` on reuse, after the existing completion guards establish that previous reads are finished. Semaphores order these operations but do not replace ownership transfers. Cached backend commands retain these handoffs without adding queue submissions, and the profiled batch span includes the final source release. Context creation initializes layouts, so source uploads follow context creation. This applies independently of the bridge, VRR and presentation mode; scaling without Frame Generation retains local image ownership.

## Admission and peak memory

Admission is an estimate, not an allocation reservation, performance guarantee, or continuously enforced memory cap. Driver requirements, pool padding, other processes, and the separate backend device can affect allocation success. Budget queries occur at admission boundaries. Gameplay FPS alone cannot authorize recreation.

Steady-state usage and replacement peaks answer different questions. A live Flow Scale, model, or capacity change constructs a complete candidate while the current resources remain usable. Until drain and handoff finish, both sets remain allocated. Deferred backend contexts and lower WSI swapchains can extend that overlap. Do not interpret the cold graph estimate as an exact prediction of this transient peak.

Frame Generation `0x` stops generation work while retaining resources when provisioning succeeded, so selecting it is not a request to reclaim memory. FP16 arithmetic also does not imply that SDR image allocation sizes are halved; image formats, geometry, graph selection, and output capacity determine the allocation demand.

## Replacement, retirement, and process exit

Private replacement follows the existing prepare/drain/commit coordinator. Preparation failure discards the candidate, keeps the active resources, and schedules a retry. A superseded candidate is discarded. Completion checks concern framegen-vulkan-owned work; private transitions do not introduce a device-wide `vkDeviceWaitIdle`. See the [private replacement contract](RUNTIME-TRANSITIONS.md#private-replacement-contract) for the complete policy.

Backend context close waits up to 250 ms for that context's work. If completion cannot be established, it moves the context to a retirement list. Subsequent context opens/closes poll that list without blocking and reclaim completed entries. After collection, opening another context is rejected when at least two contexts remain retired. This is an admission guard against accumulating unresolved work, not proof that a timed-out context is safe to free.

The application-device render fence is resolved before any generated-image preacquisition or acquire-semaphore reuse. If its bounded wait expires, the current plan holds no generated images and can present the real frame natively. Recovery polls the outstanding work without blocking before warming history and resuming generation; it never recycles an unresolved fence or command buffer.

Lower WSI swapchain retirement is separate. Maintenance fences, same-surface replacement progress, compositor grace, custom allocator callbacks, and terminal surface/device destruction determine when those handles can be released. The [lifecycle destruction policy](LIFECYCLE.md#destruction-and-retirement) owns those conditions; backend completion alone does not prove presentation retirement.

The layer calls `backend::makeLeaking()` after provisioning Frame Generation to preserve the private backend Vulkan owner during teardown and avoid loader-destruction hazards in mixed layer stacks. The backend instance destructor moves that Vulkan owner into deliberately retained storage. The operating system reclaims it when the process exits. This exception is distinct from ordinary context retirement and does not make all per-context images permanent. Standalone backend consumers do not enable it merely by constructing an instance.

## Reading memory evidence

One-second private-present phase windows maintain a small fixed set of statistics on the frame path; they add no GPU queries and complement the existing application-boundary timers. Validate the complete enabled log path with fgvk Gym's paired diagnostics-overhead mode.

Use [diagnostics](COLLECT_DIAGNOSTICS.md) to retain transition and retirement evidence. Compare repeated equivalent states after warmup and completed retirement. A temporary overlap, pool slack, or retained Off state alone is not evidence of a leak. Repeated growth in settled live allocations, descriptor counts, or process memory needs investigation against the owning lifetime.

Exercise both FP32 and FP16 for affected AMD Frame Generation paths and record untested architectures, drivers, runtimes, and rows explicitly.
