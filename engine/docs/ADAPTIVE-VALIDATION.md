# Fixed validation

Fixed Frame Generation needs two kinds of evidence: deterministic policy tests for presentation decisions, and real Vulkan tests for drivers, presentation, compositor behavior, GPU work, and game behavior. Passing one does not substitute for the other.

## Portable policy tests

From `engine/`, run:

```bash
scripts/test-adaptive-scheduler.sh
FGVK_ENABLE_SANITIZERS=ON scripts/test-adaptive-scheduler.sh
```

The script builds only the portable-policy targets. It supplies deterministic clocks and needs no Vulkan device, runtime loader, `Lossless.dll`, or Linux host. Vulkan, X11 and XCB headers are required by the Vulkan-facing policies and surface-adapter fixture; no live window-system connection is needed. Coverage includes:

- warm-up and reset boundaries;
- Fixed refresh budgeting and direct ordered-FIFO acquire recovery;
- generated-frame request, admission, scheduling, and delivery accounting;
- acquire and present recovery policy, private-transition state, and swapchain retirement; and
- native Fixed output handoff and profile-update pacing.

The Linux package build runs the full registered CTest suite, which includes these policy tests. [Testing framegen-vulkan](../../TESTING.md) owns the complete portable checklist.

## Scheduling contract

Fixed planning is deterministic. It selects the configured multiplier minus one generated frames, one to four, and returns a `GeneratedFramePlan` whose interpolation timestamps are stored inline without per-frame heap allocation.

The presentation path keeps three facts separate:

1. **Requested:** timestamps chosen by the Fixed policy.
2. **Admitted:** generated images the active transport can accept.
3. **Scheduled:** timestamps actually sent to the backend.

Full admission preserves requested timestamps. A batch admitted before backend work is evenly re-spaced across the real-frame interval when only part of it fits instead of taking an early prefix. The original real frame is outside the generated plan and keeps priority on failure.

Normal ordered SDR preserves the 3.3 sequential FIFO acquire contract, with bounded waits and zero-wait retries after pressure. [Transport recovery](#transport-recovery) owns the acquire deadlines, returned-image turnover proof, and retry rules. Allow Tearing does not select another policy because framegen-vulkan's private ordered SDR swapchain remains FIFO.

Admission pressure does not change the configured multiplier. This also applies to zero-wait preflight in a headroom-tight pool, including Game Swapchain Images compatibility: an unavailable image skips the unavailable generated outputs for that batch and admission is retried on the next real frame. Qualified ordered-acquire recovery retains its separate load-failure contract, and partial headroom pre-admission can lower the capacity for that WSI context until game-owned recreation.

### Fixed pacing paths

This map covers Frame Generation on framegen-vulkan's ordered SDR transport. FIFO describes the ordered pacing policy here. framegen-vulkan does not read compositor VRR or refresh feedback, so the rows below describe the native pacing that applies. The [WSI isolation guide](WSI-ISOLATION.md#presentation-and-swapchain-policy) owns transport details.

| Mode or boundary | Native pacing |
| --- | --- |
| Fixed 2x–5x | Exact configured multiplier, or the fractional display budget when a refresh rate is known. An explicit Base FPS Cap or acquire recovery keeps the budget path. The full-batch FIFO request needs a confirmed compositor refresh match and is inactive natively. |

Explicit caps retain their documented authority. Fixed generated-image acquisition and direct-failure recovery use the same sequential contract. Live policy changes can reset affected pacing helpers without changing the multiplier or recreating the swapchain. These are framegen-vulkan plan and queueing rules; they do not prove physical scanout timing.

The ordered SDR path uses the shared bounded output timeline when framegen-vulkan owns the negotiated Google timing namespace. FIFO annotations alone do not guarantee that a generated batch is delivered intact when several images become ready together. Distinct future timestamps preserve each output; lower present-call counts remain submission evidence and must not be described as physical scanout. See [WSI isolation](WSI-ISOLATION.md) for capability and application-timing guards.

### Fixed mode

Fixed uses the configured 2x–5x multiplier. When a nonzero refresh rate is known, a fractional display budget normally suppresses outputs that the display cannot consume; without a known refresh rate, exact Fixed behavior is retained. The budget retains both early and late source-timestamp deviations, with at most one output of carried credit. Balanced timing jitter therefore cannot progressively suppress generated frames at an exact-fit cadence, while a slow period cannot build an unbounded reserve that defeats the display ceiling after the source accelerates.

With Smooth Cadence enabled and ordered SDR transport, Fixed could request its full configured multiplier and let ordered FIFO backpressure pace real frames. That request needs a confirmed compositor refresh match, which framegen-vulkan no longer reads, so it is inactive natively. The display budget continues to observe source cadence so a transition out of this policy restores the applicable budget without a cold start. First-frame and long-stall guards remain active. Fixed retains its normal fractional display budget otherwise.

### Output timing within an existing base cap

On direct ordered transport, capped Fixed can prepare and space outputs during the existing source-cap wait and returns to the game no earlier than the original cap deadline. Plan cadence uses that reserved deadline; resource timeouts retain wall time. Interpolation timestamps and generated counts stay with the plan. Output slots must fit between completed CPU preparation and the source deadline, otherwise ordinary delivery applies. Late arrivals, loading stalls, native preference/probes, partial admission, live policy changes, and unsupported batches discard output timing state instead of accumulating catch-up debt. This is bounded use of cap slack, not a guarantee of even delivery below the cap or with an uncapped source. Preparation stays after the source-cap wait while generated-image admission is under pressure or the returned image pool cannot fit the active policy’s maximum generated batch, preserving zero-wait retry and higher-rung qualification opportunities. Application-owned timing and active acquire recovery retain their current path. Renderer-owned Google or EXT timing uses its compositor output clock instead of CPU output deadlines. Validate source intervals and independent compositor completion separately.

Renderer-owned Vulkan timing can prepare inside the same source-cap interval for scaled output. It keeps its own ordered output clock instead of adding CPU output deadlines. The existing source deadline limits submission backpressure for that batch; display targets, queue readiness, generated counts and real-frame presentation waits remain unchanged. Control returns to the application no earlier than the reserved cap deadline. This prevents cap sleeping followed by output spacing from consuming part of the next source interval. The same timing-owner, image-capacity and admission-pressure guards apply, and every application present clears the previous batch’s submission budget.

Exact Fixed uses the same bounded output owner when an explicit Base FPS Cap and the complete configured 2x–5x batch fit within a confirmed refresh rate. Native FIFO also admits this preparation without compositor refresh feedback, independently of Smooth Cadence; otherwise sleeping before backend preparation leaves the cap interval unavailable and produces paired output bursts. Its output rate is the cap multiplied by the configured multiplier. For example, a 30 FPS cap with Fixed 2x on a 120 Hz display schedules outputs about 16.67 ms apart instead of submitting a pair together every 33.33 ms. Partial batches, history warm-up, disabled generation, slow preparation and late source frames retain ordinary delivery. The existing source-return deadline is preserved. Native worker admission follows the bounded handoff contract below; no additional cap or setting is introduced.

Native desktop FIFO and MAILBOX/IMMEDIATE can use the existing Fixed cap slack without compositor refresh feedback. Native FIFO Fixed also keeps this cap spacing when the caller supplies per-present timing: those targets belong to the final real image and do not schedule the generated images. framegen-vulkan preserves the caller target, ID and fence on that real image and spaces submissions within its already configured cap interval; it does not allocate a timing namespace or rewrite the caller target. Caller timing still excludes cap preparation on other transports, and compositor-owned clocks retain their existing rules. Fixed Smooth Cadence additionally spaces complete GPU-ready batches when a game-owned limiter or a late arrival leaves no framegen-vulkan cap slack. `RealFramePacer` qualifies a median source period from eight unpaced intervals. Synchronous delivery reserves the output span before waiting on the existing backend timeline. An admitted worker instead waits on the final already-submitted backend output value within the source-readiness deadline, bounded to 50 ms, while the producer starts its next frame. Expired readiness drains all retained images through ordinary semaphore-protected delivery without timed catch-up slots. The fallback starts at readiness and retains at least one output interval between subsequent CPU submissions, so a late acquire or sleep cannot replay expired slots. Measured pacing waits are excluded when identifying sustained slower application work; eight consecutive slower samples trigger unpaced requalification. Complete recent windows refine the estimate downward without selecting only their faster arrivals. Two consecutive source intervals at least one eighth of an output slot shorter than the retained period release the old fallback spacing and qualify the new source directly from eight unpaced intervals. The margin follows the configured batch size so higher multipliers cannot hide recovery behind their longer output spans. A complete eight-sample paced window also supplies paired full-interval and wait-excluded medians: two improvements against both baselines release stale spacing when a relative game limiter hides a modest speedup relative to the initial unpaced period. Readiness time can trade with an absolute game limiter while full source cadence stays constant; a wait-excluded change alone cannot authorize requalification. The same paired baselines detect sustained slower work even when the interval remains longer than the initial unpaced period; eight consecutive slower samples trigger requalification. Pending faster/slower confirmation freezes the reference so a partial window cannot absorb the change before confirmation. Unpaced or interrupted windows cannot establish that baseline; elapsed CPU time excluding waits is not a GPU execution measurement. This prevents a raised game cap, or removal of a game cap below an existing framegen-vulkan cap, from gradually accelerating through its own old output sleeps. Ordinary alternating jitter cannot accumulate acceleration evidence across slower arrivals. A gap exceeding two source periods skips additional fallback waits, clears the partial sample window and retains the previous estimate for normal arrivals. Eight consecutive such intervals below the 250 ms interruption bound release the stale estimate so a sustained slower workload can qualify. Cold cap startup may take output ownership immediately. Once a source cadence has been learned, framegen-vulkan requires eight consecutive complete cap-paced batches before taking ownership from the game-owned fallback; a single fast arrival after a partial batch cannot establish that proof. Existing cap ownership is retained across brief late arrivals and loading interruptions. Those frames receive no additional GPU-ready fallback wait or output sleep; the next eligible batch resumes the existing cap deadlines. Otherwise readiness plus output spacing can consume the next source interval and sustain a below-cap loop. Eight consecutive slower-work samples, excluding measured output waits and comparing against the shorter configured-cap period while it owns output timing, release this ownership and requalify a genuinely slower game cadence. An already slower learned game period must not prevent release of a nonbinding cap. Changing or disabling the cap, losing direct Fixed eligibility, and explicit resets also discard ownership. A nonbinding framegen-vulkan cap that has not spaced a complete batch leaves the game-owned fallback available. These rules bound timing debt and avoid amplifying a loading hitch into a growing delay.

Native FIFO can use this same GPU-ready fallback when Fixed Smooth Cadence is enabled and no caller, owned Vulkan or compositor timing clock controls output. With no framegen-vulkan cap, Fixed uses it with Smooth Cadence off too whenever the output worker can deliver the batch: unspaced, the generated image reached FIFO about 0.1 ms before its real image and the compositor discarded most generated frames. The worker adds no wait to the application present. It learns the actual source cadence, including a game cap below a nonbinding framegen-vulkan cap; it does not assume cap × multiplier is the delivered output rate. Enabled timing, ID and present-wait/wait2 capabilities alone do not exclude this fallback: it consumes no feedback namespace or present ID, and caller waits keep their total timeout and driver completion result after any retained-ID handoff. Actual per-present timing nodes retain output-clock ownership. A blocking wait for the latest retained ID does not release this fallback, whether it runs on the producing thread or a separate waiter gating the producer through a frame-latency event; completion-paced delivery stays ordinary. The worker's measured wait is excluded from source-work learning; overlapping multi-frame production retains its existing cadence owner. The completion spiral check is log only. For three consecutive one-second windows, each one must show the learned source period growing by more than 10% against the previous window, the mean completion wait per source growing too, and that mean covering at least half of the period growth. The mean is the window's summed wait divided by its sources, so a lower frame rate does not hide the growth. The check then prints `framegen-vulkan: completion spiral suspected: period_ms=… completion_wait_ms=… windows=3 context=…` once per episode, and `completion spiral cleared` when the growth stops. Its rule is the pure `CompletionSpiralDetector` (`completion_spiral.hpp`), tested by `completion-spiral`. The WSI guide owns the exact handoff, timeout and attribution rules. Caller IDs, fences and frame timing remain solely on the final real image; generated outputs inherit only a persistent mode override. FIFO_RELAXED and FIFO Latest Ready are not admitted by this policy. Native FIFO Fixed 2x–5x may use the existing bounded output worker under the [WSI handoff contract](WSI-ISOLATION.md). Its worker readiness wait stays within one observed source period; the complete batch can overlap next-frame work, including GPU readiness and its first output deadline. At most four generated images and the existing real image are retained, with no second source batch and no new GPU allocation. Synchronous and retained native outputs share one private presentation queue from the context’s first present, so timing or live-policy transitions cannot split presentation order across queues. GPU copies remain on the original graphics queue and signal the existing binary waits. No present mode, timing namespace, extension, cap or generated-frame plan changes.

An admitted native Fixed worker owns backend readiness and every output of the batch, including cap-owned batches with Smooth Cadence off. The cap retains its original application-return deadline unless the [release-point source cap](WSI-ISOLATION.md#release-point-source-cap) owns it; that path returns the present immediately and spaces the batch from GPU readiness on the cap's output interval. A retained batch continues the previous output phase by at most three quarters of an output slot, so its final output leaves before the next source normally arrives and the next present or acquire does not join the worker on the producing thread. GPU readiness shifts the whole output batch when necessary; ordinary worker wake lateness does not accumulate into its source-period estimate. Without an admitted output worker, backend readiness, output spacing and lower presentation remain synchronous. If that time plus work outside framegen-vulkan exceeds the game-limiter interval, source throughput falls even when backend GPU execution alone fits comfortably. Games that sleep a full frame interval after present returns can run slower as well, although framegen-vulkan does not add a second configured source cap. This path does not guarantee game-cap throughput or physical frame pacing. Partial batches, history warm-up, capped Smooth Cadence Off without the release-point cap, and application/compositor timing retain their existing owners. Live policy/resource resets discard learned source cadence. No present-wait extension is required. CPU submission spacing is separate from physical scanout, and rates that do not divide a fixed refresh rate still face display quantization.

The release-point cap has a separate queued-source qualification rule: it measures a complete eight-interval elapsed-time window, allowing short submissions and their compensating long GPU waits to contribute together. A long pause discards that window, and changing between released and ordinary delivery resets qualification. The measured throughput can lengthen output spacing below a nonbinding cap without moving the cap. A readiness miss skips an unacquired worker-copy generated image through its semaphore-protected continuation, while the real image remains deliverable. A generated image that was already presented retains its real output slot across joins. Overlap acquisition waits for one free image without draining future batches; [WSI isolation](WSI-ISOLATION.md#release-point-source-cap) owns the timeout and image-pressure details.

## Transport recovery

Fixed ordered generated-image acquisition uses one application-present deadline, not a refresh-derived slow-call threshold per generated image. Each image receives only the remaining cumulative configured budget. An unconfigured Fixed path with relief headroom retains its unbounded compatibility contract. When the image pool fits the Fixed batch but lacks an additional relief image, the shared deadline is at most 50 ms; a shorter configured deadline wins. Headroom-tight admission remains nonblocking. Normal ordered delivery preserves the established sequential FIFO acquisition point. Fixed refresh retains the configured sequential acquire contract from 3.3. Returned image count and batch size determine the turnover proof, independently of refresh rate, source FPS, device identity, or a timer.

A `VK_TIMEOUT`/`VK_NOT_READY` result, exhaustion of the configured cumulative acquire budget, or completion of an ordered batch after that cumulative wall-clock budget has been reached starts blocking ordered transport recovery. The deadline is the explicit application-present budget; it is not derived from output FPS, GPU load, device, resolution, or post-processing cost. Fixed deadline failures enter the ordered native-drain retry ladder of 250 ms, 500 ms, one, two, five, 15, and 30 seconds. Recovery probes retry one image using the explicit configured acquire budget or one confirmed display period, and without either contract the retry is nonblocking. There is no FPS-derived acquire deadline, native-cadence hold, repeated-episode counter, failure-count-derived acquire timeout, or timed recovery window.

An explicit live generation-policy transition arms one one-shot recreation permission. Multiple policy writes before the transition is applied are last-value-wins: generation remains suspended, and that transition owns the single transport permission. The first generated-image acquire batch completed within its configured budget consumes the permission without action. If an acquire timeout, budget exhaustion, or cumulative deadline overrun occurs first, one successful retirement-protected real present may request a game-owned recreation; the context cannot signal it twice, and a replacement context initializes from the current transition sequence so the same old event cannot rearm a loop. Fixed direct deadline failures retain bounded in-place backoff.

A recovery probe runs only when temporal history is ready and the current Fixed policy requests generated work. A real-only policy frame performs no generated-image acquisition and leaves the pending probe intact for the next eligible frame; it cannot count as a probe failure or increase recovery backoff.

Lower `QueuePresentKHR` duration is diagnostic only. A successful but slow present cannot quarantine generation, change a multiplier, warm history, or request recreation. framegen-vulkan cannot reliably distinguish compositor throttling, stacked GPU work, VRR behavior, or a game-scene change from a wedged queue by elapsed time alone.

Cadence stalls and low FPS never request swapchain recreation. Live mode, multiplier, base-cap, and Smooth Cadence changes apply a transient boundary: incomplete ordered-acquire retry state is discarded, history restarts from three frames, and the one-shot direct-failure permission is armed. Fixed never launches a cadence-collapse probe: its user-selected multiplier remains exact unless a direct Vulkan failure owns bounded transport safety.

`GeneratedDeliveryWindow` compares requested outputs with outputs queued inside framegen-vulkan's budget. It does not claim compositor scanout. Diagnostics distinguish requested, admitted, scheduled, and delivered counts.

Private Flow Scale, model, or generated-capacity changes retain the old policy while replacement resources are prepared. Capacity growth that does not fit the current WSI pool remains pending for game-owned recreation. [Runtime configuration transitions](RUNTIME-TRANSITIONS.md) owns that lifecycle. Ultra Performance is a restart-bound resource policy.

## Runtime validation

The external-recovery inventory pairs unidentified-overlay controls across Fixed 2x and 3x and Frame Generation-only operation. Pause, covered-throttle, and repeated short/long journeys must independently prove source recovery, target-output recovery, focus sequencing, fresh history, generation suspension where applicable, and context stability. Portable policy tests separately cover Smooth Cadence mode, 2x–5x multipliers, exact Fixed stability, transition-scoped acquire failure, inert successful transport, and the absence of FPS-authorized recovery so hardware rows do not carry the full combinatorial burden.

For affected changes, cover these runtime boundaries:

| Boundary | Minimum evidence |
| --- | --- |
| Generation modes | Live `0x`, Fixed 2x and affected higher multipliers, and Smooth Cadence. |
| Cadence changes | Startup, gameplay rate changes, true fixed-rate rejection, short hitches, long interruptions, and fast-present bursts. |
| Presentation | Ordered SDR, explicit acquire failure, configured cumulative acquire-deadline overrun, slow lower-present non-authority, focus and overlays, resize, recreation, and shutdown. |
| Resource transitions | Live Off/On, Flow Scale or model replacement, capacity growth with and without WSI headroom, and history warm-up. |
| API/runtime | Affected native Vulkan, DXVK, VKD3D-Proton, direct desktop, Flatpak, architecture, and Proton-family paths. |
| Quality/performance | Real FPS, displayed FPS, frame-time percentiles, generated share, visible artifacts, latency impression, GPU time, and memory where relevant. |

Record the commit and build identity, hardware, driver, compositor, runtime, game and resolution, policy settings, transitions, diagnostic path, and verdict. Mark unavailable hardware or paths **not tested**.

Presentation diagnostics are opt-in and can perturb pacing. Use the `recovery` and `performance` presets for a separate diagnostic run, then disable them for subjective comparison. Their timestamps describe framegen-vulkan policy and queueing, not compositor scanout.

## Release gates

An affected candidate is ready for broader testing when:

1. portable and sanitizer policy tests pass;
2. affected Fixed multipliers stay within their configured counts;
3. no case enters an unexpected indefinite wait, recreation loop, or permanent unintended native-only state;
4. Off/On and recreation restart from valid temporal and recovery state;
5. failures have context-correlated diagnostics; and
6. unavailable rows and known title-specific failures are recorded.

## Native Fixed output handoff validation

An admitted native detached Fixed worker can qualify ready-output spacing with Smooth Cadence off whether the configured source cap is zero, binding or nonbinding. Cap-owned preparation and release-gated scheduling retain precedence over the ordinary ready fallback. The `profile-update` regression combines actual eligibility and the canonical pacer for caps 0, 610 and 60 across 60 → 30 → 100 → 30 FPS sources, checking half-source-period slots after qualification, no source hold from nonbinding caps, and binding-cap takeover/release. Timing owners, recovery, and disabled generation retain their exclusions. This changes no saved cap value or cap semantics.

Native Fixed's bounded output handoff is specified in [WSI isolation](WSI-ISOLATION.md). Its `deferred-present` portable test covers copied inputs and retirement fences, one-slot admission, acquire-style polls/timeouts, actual error retention, repeated handoff, worker teardown and shared private-queue serialization. Queue-reservation tests preserve caller storage and indices, reject protected queues and account for all requests against physical family capacity. Scheduling estimators and readiness-before-spacing remain owned by `RealFramePacer`; the worker delivers only the current bounded native output batch. Qualify early versus late acquisition, game CPU load, pipeline acquisition, mode changes, replacement, idle/destruction and driver errors on hardware.


An actually queued native real output supplies detached-output evidence for the next source observation. Across a complete eight-sample detached window, the pacer updates the full-source median in either direction while retaining output spacing. Paired early/late arrivals and short acquisition joins must not enter the synchronous two-faster-sample release path or trigger eight unpaced batches; a one-way minimum must not ratchet the interval toward faster jitter. Acquisition waits remain measured source-wait cost, but do not change how the preceding output was submitted. Two consecutive full intervals at least one quarter shorter retune large recovery debt; four consecutive faster samples using the existing full-interval and wait-excluded work tests retune smaller sustained improvements. Detached acceleration shortens the interval in place without clearing the qualified period or discarding the source window. Its slower samples still correct an early-arrival estimate. Longer runs of early arrivals can pass a consecutive-sample threshold without a genuine mean-rate change, so no such threshold may create eight unpaced batches. Synchronous delivery retains its release-and-requalify rule because its output sleeps can hide the source cadence. Merely having a private queue or an idle worker does not supply detached evidence. `testDetachedOutputSourceJitter` checks balanced 60 FPS jitter with runs of two, four, six and sixteen early/late intervals and brief acquisition joins, genuine faster/slower 70/80 FPS changes, sustained slower arrivals and repeated workload recovery with actual detached-slot acquisition feedback, including 8 ms readiness that conceals a smaller speedup.

A readiness miss must not erase an established detached cadence episode. An underestimated interval can make preparation exceed its budget; treating that unpaced batch as synchronous removes the slower-window correction and can cause repeated qualification gaps. `testDetachedCadenceAfterReadinessMiss` feeds four early and four compensating late source arrivals through actual bounded readiness decisions, requires recovery to the original spacing, and limits cascading misses. A synchronous paced batch or policy reset ends the episode.

Native Fixed 2x cap-owned batches on the same eligible private-queue path also establish backend readiness on the worker within one full source period from arrival, bounded at 50 ms. A first-slot miss before that deadline moves the output phase later without shortening output intervals or moving the application source-cap clock; final real delivery uses the existing bounded handoff. The worker retains at most one source batch; it never queues a second batch to recover output debt. `testLateNativeFixedCapKeepsSpacing` checks late preparation, complete within/between-batch spacing, unchanged source-cap deadlines, rejection of whole-period debt, and isolation from target-clock pacing. A short source-cap miss may use the ready fallback only after actual detached delivery has established its cadence episode; private queue availability alone cannot authorize that wait. Long source interruptions still skip it. Eight consecutive slower detached arrivals without another cap-paced batch release cap ownership without discarding the learned period. `testDetachedCapYieldsToGameLimiter` covers the transition from a 70 FPS framegen-vulkan cap to a 60 FPS game limiter. GPU timeout and other transports retain their existing fallback. This adds no worker, queued image, allocation, query or presentation extension.

Detached ready batches retain one output phase across source boundaries. The next first slot follows the previous real slot, rebased from the worker’s actual lower-call start when delivery is more than half a slot late. Ordinary wake lateness stays on the absolute phase rather than extending every period. Early readiness may reserve less than one additional output interval; it never makes the game thread wait for that first slot. Exhausting that bound releases only the cross-batch phase for two observation windows, ensuring one complete eight-sample window without phase holds at any window alignment while preserving within-batch spacing and the qualified source estimator. Two samples of improved wait-excluded work hidden by measured acquisition joins and a preceding first-slot hold can release the same phase; GPU-readiness changes alone cannot. Missing or synchronous delivery, count/owner changes, policy reset and errors discard the ready phase; cap-owned and compositor clocks retain their existing owners. `testDetachedBatchPhaseContinuity` exercises steady source intervals, alternating 4/7 ms readiness, uncapped entry and a late worker wake across 2x–5x, checking every boundary rather than only batch intervals. `testDetachedBatchPhaseRecovery` feeds relative and absolute producer limits through readiness, complete-batch retention and acquisition joins, requiring recovery from 20 to 40 FPS and back without an old-phase throughput lock. `testDetachedBatchWakeFeedback` additionally feeds 2,400 source frames through pending GPU work, acquisition joins and repeated 100 µs worker lateness, requiring stable learned intervals and source throughput. These are deterministic scheduling checks, not displayed-motion evidence.
