# Adaptive validation

Adaptive Frame Generation needs two kinds of evidence: deterministic policy tests for scheduler decisions, and real Vulkan tests for drivers, presentation, compositor behavior, GPU work, and game behavior. Passing one does not substitute for the other.

## Portable policy tests

From `engine/`, run:

```bash
scripts/test-adaptive-scheduler.sh
FGVK_ENABLE_SANITIZERS=ON scripts/test-adaptive-scheduler.sh
```

The script builds only the portable-policy targets. It supplies deterministic clocks and needs no Vulkan device, runtime loader, `Lossless.dll`, or Linux host. Vulkan, X11 and XCB headers are required by the Vulkan-facing policies and surface-adapter fixture; no live window-system connection is needed. Coverage includes:

- warm-up, ramping, multiplier ceilings, target behavior, and reset boundaries;
- Fractional placement, near-target native preference, Smooth Cadence, and cadence recovery;
- manual-target restoration;
- Fixed refresh budgeting and direct ordered-FIFO acquire recovery;
- generated-frame request, admission, scheduling, and delivery accounting;
- acquire and present recovery policy, private-transition state, and swapchain retirement; and
- trace replay plus the scheduler matrix.

The matrix runs 384 combinations of source cadence, target, multiplier ceiling, and Smooth Cadence. Each simulation reports complete generated delivery and measures the final five seconds of a 25-second run, allowing every higher rung to qualify before measuring settled output. To keep its CSV output:

```bash
cmake -S . -B build/adaptive-policy \
  -DFGVK_BUILD_VK_LAYER=OFF \
  -DFGVK_BUILD_CLI=OFF \
  -DBUILD_TESTING=ON
cmake --build build/adaptive-policy --target fgvk-adaptive-matrix
build/adaptive-policy/fgvk-render/fgvk-adaptive-matrix > adaptive-policy-matrix.csv
```

For a same-machine CPU-cost comparison, run `scripts/benchmark-adaptive-scheduler.sh`. Its nanoseconds-per-decision results are not portable performance limits.

The Linux package build runs the full registered CTest suite, which includes these policy tests. [Testing framegen-vulkan](../../TESTING.md) owns the complete portable checklist.

## Scheduling contract

`AdaptiveScheduler::planFrame()` is deterministic. It observes real-frame cadence, selects zero to four generated frames, and returns a `GeneratedFramePlan` whose interpolation timestamps are stored inline without per-frame heap allocation.

The presentation path keeps three facts separate:

1. **Requested:** timestamps chosen by Fixed or Adaptive policy.
2. **Admitted:** generated images the active transport can accept.
3. **Scheduled:** timestamps actually sent to the backend.

Full admission preserves requested timestamps. A batch admitted before backend work is evenly re-spaced across the real-frame interval when only part of it fits instead of taking an early prefix. The original real frame is outside the generated plan and keeps priority on failure.

Normal Adaptive ordered SDR preserves the 3.3 sequential FIFO acquire contract, with bounded waits and zero-wait retries after pressure. [Transport recovery](#transport-recovery) owns the acquire deadlines, returned-image turnover proof, and retry rules. Allow Tearing does not select another policy because framegen-vulkan's private ordered SDR swapchain remains FIFO.

Admission pressure does not directly demote an already validated scheduler load. This also applies to zero-wait preflight in a headroom-tight pool, including Game Swapchain Images compatibility: an unavailable image skips the unavailable generated outputs for that batch and admission is retried on the next real frame, without a one-second stabilization or multiplier retry backoff. A headroom miss during an active multiplier evaluation can still reject that experiment, and qualified ordered-acquire recovery retains its separate load-failure contract. Sustained delivery loss can still reject an active multiplier through its normal delivery window, while partial headroom pre-admission during a multiplier evaluation can lower the capacity for that WSI context until game-owned recreation.

### Fixed and Adaptive pacing paths

This map covers Frame Generation on framegen-vulkan's ordered SDR transport. FIFO describes the ordered pacing policy here. framegen-vulkan does not read compositor VRR or refresh feedback, so the rows below describe the native pacing that applies. The [WSI isolation guide](WSI-ISOLATION.md#presentation-and-swapchain-policy) owns transport details.

| Mode or boundary | Native pacing |
| --- | --- |
| Fixed 2x–5x | Exact configured multiplier, or the fractional display budget when a refresh rate is known. An explicit Base FPS Cap, Dynamic Cadence Recovery, or acquire recovery keeps the budget path. The full-batch FIFO request needs a confirmed compositor refresh match and is inactive natively. |
| Fractional Adaptive with variable generated counts | Keep the target-output clock and the selected real/generated ratio; place admitted timestamps evenly within the real-frame interval. |
| Fractional Adaptive with an accepted constant integer cadence | Retain the accepted generated count instead of the moving target clock. A FIFO handoff needs a confirmed compositor refresh match and is inactive natively. |
| Steady Adaptive at a proven 2x | Keep scheduler pacing. A FIFO handoff needs a confirmed compositor refresh match and is inactive natively. |
| Steady Adaptive at a validated 3x–5x | Keep scheduler/target-clock pacing; after one second of qualifying cadence, refine the automatic base cap to target divided by the active constant multiplier, or the validated multiplier when no constant plan is active. Accepted 2x retains the normal half-target cap. Release a higher cap after sustained loss or a safety transition. The full-batch FIFO handoff needs a confirmed compositor refresh match and is inactive natively. |
| Adaptive generated-image acquire pressure | Use the configured sequential FIFO acquire contract; an explicit timeout, budget exhaustion, or a completed batch that reaches the configured cumulative acquire deadline can enter ordered native-drain recovery. |

Dynamic Cadence Recovery and explicit caps retain their documented authority. Fixed generated-image acquisition and direct-failure recovery use the same sequential contract. Live policy changes can reset affected pacing helpers without resetting the Adaptive scheduler, changing its validated multiplier, or recreating the swapchain. These are framegen-vulkan plan and queueing rules; they do not prove physical scanout timing.

The ordered SDR path uses the shared bounded output timeline when framegen-vulkan owns the negotiated Google timing namespace. FIFO annotations alone do not guarantee that a generated batch is delivered intact when several images become ready together. Distinct future timestamps preserve each output; lower present-call counts remain submission evidence and must not be described as physical scanout. See [WSI isolation](WSI-ISOLATION.md) for capability and application-timing guards.

### Fixed mode

Fixed uses the configured 2x–5x multiplier. When a nonzero refresh rate is known, a fractional display budget normally suppresses outputs that the display cannot consume; without a known refresh rate, exact Fixed behavior is retained. The budget retains both early and late source-timestamp deviations, with at most one output of carried credit. Balanced timing jitter therefore cannot progressively suppress generated frames at an exact-fit cadence, while a slow period cannot build an unbounded reserve that defeats the display ceiling after the source accelerates.

With Smooth Cadence enabled and ordered SDR transport, Fixed could request its full configured multiplier and let ordered FIFO backpressure pace real frames. That request needs a confirmed compositor refresh match, which framegen-vulkan no longer reads, so it is inactive natively. The display budget continues to observe source cadence so a transition out of this policy restores the applicable budget without a cold start. First-frame and long-stall guards remain active. Fixed retains its normal fractional display budget otherwise.

### Adaptive mode

Adaptive varies generated work toward `target_fps` without exceeding `adaptive_max_multiplier`. Fractional mode normally owns the long-term output budget and keeps timestamps evenly spaced within each real-frame interval. Near target, it may prefer native presentation when measured interval quality and output coverage are already sufficient.

#### Fractional real-frame priority

`adaptive_fractional_real_frame_priority = auto` is the default and adds no real-frame cap. With Base FPS Cap off or at least the target, qualified native presentation may exceed the Adaptive target up to the display ceiling, while the source pacer continues to enforce any manual cap. Only these eligible Fractional Automatic profiles additionally qualify sustained at/above-target cadence through the existing one-second hold; the output floor, quality checks and exit hysteresis remain authoritative. Steady, explicit priorities, below-target manual caps and Fixed recovery retain their previous scheduler qualification rules. Both owned timing paths release the target ceiling and generated-work readiness lead only while that qualified native phase owns presentation. Occasional real-only Fractional turns, warm-up, native probes and recovery keep their existing generated timeline. Smooth Cadence on/off and multiplier ceilings share this policy. A faster source hidden by generated backpressure still needs Dynamic Cadence Recovery to become observable.

Explicit Low, Medium, High, and Very High priorities apply target-relative real-frame caps using 3:2, 2:1, 3:1, and 4:1 real/generated ratios. At a 120 FPS target those caps are 72, 80, 90, and 96 real FPS. The explicit cap takes precedence over the manual cap only while Fractional Adaptive is active; Fixed and Steady ignore it. Below-target manual caps, explicit priorities and Steady retain their output pacing. A priority or target change resets the real-frame pacer and affected scheduler policy through the ordinary live profile transition.

#### Output timing within an existing base cap

On direct ordered transport, capped Fractional can prepare and space outputs during the existing source-cap wait. It keeps one target-output clock across changing batch sizes and returns to the game no earlier than the original cap deadline. Scheduler cadence uses that reserved deadline; resource timeouts retain wall time. Interpolation timestamps and generated counts stay scheduler-owned. Output slots must fit between completed CPU preparation and the source deadline, otherwise ordinary delivery applies. Late arrivals, loading stalls, native preference/probes, partial admission, live policy changes, and unsupported batches discard output timing state instead of accumulating catch-up debt. This is bounded use of cap slack, not a guarantee of even delivery below the cap or with an uncapped source. Preparation stays after the source-cap wait while generated-image admission is under pressure or the returned image pool cannot fit the active policy’s maximum generated batch, preserving zero-wait retry and higher-rung qualification opportunities. Target-matched automatic pacing on direct FIFO, active acquire recovery and application-owned timing retain their current path. Renderer-owned Google or EXT timing uses its compositor output clock instead of CPU output deadlines. Validate source intervals and independent compositor completion separately.

Renderer-owned Vulkan timing can prepare inside the same source-cap interval, including target-matched automatic Adaptive caps, scaled output. It keeps its own ordered output clock instead of adding CPU output deadlines. The existing source deadline limits submission backpressure for that batch; display targets, queue readiness, generated counts and real-frame presentation waits remain unchanged. Control returns to the application no earlier than the reserved cap deadline. This prevents cap sleeping followed by output spacing from consuming part of the next source interval. The same timing-owner, image-capacity and admission-pressure guards apply, and every application present clears the previous batch’s submission budget.

Without a compositor output clock, Adaptive automatic caps can use this interval only when the target is strictly below the confirmed refresh rate, with Smooth Cadence either on or off. The scheduler still chooses every generated count and interpolation timestamp. Preparation does not choose an Adaptive rung or replace cap refinement, FIFO handoff or recovery. Unknown refresh cannot qualify automatic early preparation.

Exact Fixed uses the same bounded output owner when an explicit Base FPS Cap and the complete configured 2x–5x batch fit within a confirmed refresh rate, with Dynamic Cadence Recovery disabled. Native FIFO also admits this preparation without compositor refresh feedback, independently of Smooth Cadence; otherwise sleeping before backend preparation leaves the cap interval unavailable and produces paired output bursts. Its output rate is the cap multiplied by the configured multiplier; the saved Adaptive target has no effect. For example, a 30 FPS cap with Fixed 2x on a 120 Hz display schedules outputs about 16.67 ms apart instead of submitting a pair together every 33.33 ms. Partial batches, history warm-up, disabled generation, slow preparation and late source frames retain ordinary delivery. The existing source-return deadline is preserved. Native worker admission follows the bounded handoff contract below; no additional cap or setting is introduced.

Native desktop FIFO and MAILBOX/IMMEDIATE can use the existing Fixed cap slack without compositor refresh feedback. Native FIFO Fixed also keeps this cap spacing when the caller supplies per-present timing: those targets belong to the final real image and do not schedule the generated images. framegen-vulkan preserves the caller target, ID and fence on that real image and spaces submissions within its already configured cap interval; it does not allocate a timing namespace or rewrite the caller target. Caller timing still excludes cap preparation on other transports and in Adaptive, and compositor-owned clocks retain their existing rules. Fixed Smooth Cadence additionally spaces complete GPU-ready batches when a game-owned limiter or a late arrival leaves no framegen-vulkan cap slack. `RealFramePacer` qualifies a median source period from eight unpaced intervals. Synchronous delivery reserves the output span before waiting on the existing backend timeline. An admitted worker instead waits on the final already-submitted backend output value within the source-readiness deadline, bounded to 50 ms, while the producer starts its next frame. Expired readiness drains all retained images through ordinary semaphore-protected delivery without timed catch-up slots. The fallback starts at readiness and retains at least one output interval between subsequent CPU submissions, so a late acquire or sleep cannot replay expired slots. Measured pacing waits are excluded when identifying sustained slower application work; eight consecutive slower samples trigger unpaced requalification. Complete recent windows refine the estimate downward without selecting only their faster arrivals. Two consecutive source intervals at least one eighth of an output slot shorter than the retained period release the old fallback spacing and qualify the new source directly from eight unpaced intervals. The margin follows the configured batch size so higher multipliers cannot hide recovery behind their longer output spans. A complete eight-sample paced window also supplies paired full-interval and wait-excluded medians: two improvements against both baselines release stale spacing when a relative game limiter hides a modest speedup relative to the initial unpaced period. Readiness time can trade with an absolute game limiter while full source cadence stays constant; a wait-excluded change alone cannot authorize requalification. The same paired baselines detect sustained slower work even when the interval remains longer than the initial unpaced period; eight consecutive slower samples trigger requalification. Pending faster/slower confirmation freezes the reference so a partial window cannot absorb the change before confirmation. Unpaced or interrupted windows cannot establish that baseline; elapsed CPU time excluding waits is not a GPU execution measurement. This prevents a raised game cap, or removal of a game cap below an existing framegen-vulkan cap, from gradually accelerating through its own old output sleeps. Ordinary alternating jitter cannot accumulate acceleration evidence across slower arrivals. A gap exceeding two source periods skips additional fallback waits, clears the partial sample window and retains the previous estimate for normal arrivals. Eight consecutive such intervals below the 250 ms interruption bound release the stale estimate so a sustained slower workload can qualify. Cold cap startup may take output ownership immediately. Once a source cadence has been learned, framegen-vulkan requires eight consecutive complete cap-paced batches before taking ownership from the game-owned fallback; a single fast arrival after a partial batch cannot establish that proof. Existing cap ownership is retained across brief late arrivals and loading interruptions. Those frames receive no additional GPU-ready fallback wait or output sleep; the next eligible batch resumes the existing cap deadlines. Otherwise readiness plus output spacing can consume the next source interval and sustain a below-cap loop. Eight consecutive slower-work samples, excluding measured output waits and comparing against the shorter configured-cap period while it owns output timing, release this ownership and requalify a genuinely slower game cadence. An already slower learned game period must not prevent release of a nonbinding cap. Changing or disabling the cap, losing direct Fixed eligibility, and explicit resets also discard ownership. A nonbinding framegen-vulkan cap that has not spaced a complete batch leaves the game-owned fallback available. These rules bound timing debt and avoid amplifying a loading hitch into a growing delay.

Native FIFO can use this same GPU-ready fallback when Fixed Smooth Cadence is enabled and no caller, owned Vulkan or compositor timing clock controls output. With no framegen-vulkan cap, Fixed uses it with Smooth Cadence off too whenever the output worker can deliver the batch: unspaced, the generated image reached FIFO about 0.1 ms before its real image and the compositor discarded most generated frames. The worker adds no wait to the application present. It learns the actual source cadence, including a game cap below a nonbinding framegen-vulkan cap; it does not assume cap × multiplier is the delivered output rate. Enabled timing, ID and present-wait/wait2 capabilities alone do not exclude this fallback: it consumes no feedback namespace or present ID, and caller waits keep their total timeout and driver completion result after any retained-ID handoff. Actual per-present timing nodes retain output-clock ownership. An observed blocking wait for the latest retained ID on the producing thread releases this fallback for the context lifetime, preserving ordinary completion-paced delivery. A separate waiter can gate the producer through a frame-latency event too: two slower source intervals after completed latest-ID waits, with no acquisition overlapping those waits, release the same conflicting fallback. The worker's measured wait is excluded from source-work learning; overlapping multi-frame production retains its existing cadence owner. The WSI guide owns the exact handoff, timeout and attribution rules. Caller IDs, fences and frame timing remain solely on the final real image; generated outputs inherit only a persistent mode override. FIFO_RELAXED and FIFO Latest Ready are not admitted by this policy. Native FIFO Fixed 2x–5x may use the existing bounded output worker under the [WSI handoff contract](WSI-ISOLATION.md). Its worker readiness wait stays within one observed source period; the complete batch can overlap next-frame work, including GPU readiness and its first output deadline. At most four generated images and the existing real image are retained, with no second source batch and no new GPU allocation. Synchronous and retained native outputs share one private presentation queue from the context’s first present, so timing or live-policy transitions cannot split presentation order across queues. GPU copies remain on the original graphics queue and signal the existing binary waits. No present mode, timing namespace, extension, cap or generated-frame plan changes.

An admitted native Fixed worker owns backend readiness and every output of the batch, including cap-owned batches with Smooth Cadence off. The cap retains its original application-return deadline unless the [release-point source cap](WSI-ISOLATION.md#release-point-source-cap) owns it; that path returns the present immediately and spaces the batch from GPU readiness on the cap's output interval. A retained batch continues the previous output phase by at most three quarters of an output slot, so its final output leaves before the next source normally arrives and the next present or acquire does not join the worker on the producing thread. GPU readiness shifts the whole output batch when necessary; ordinary worker wake lateness does not accumulate into its source-period estimate. Without an admitted output worker, backend readiness, output spacing and lower presentation remain synchronous. If that time plus work outside framegen-vulkan exceeds the game-limiter interval, source throughput falls even when backend GPU execution alone fits comfortably. Games that sleep a full frame interval after present returns can run slower as well, although framegen-vulkan does not add a second configured source cap. This path does not guarantee game-cap throughput or physical frame pacing. Partial batches, history warm-up, capped Smooth Cadence Off without the release-point cap, application/compositor timing, Adaptive and Dynamic Cadence Recovery retain their existing owners. Live policy/resource resets discard learned source cadence. No present-wait extension is required. CPU submission spacing is separate from physical scanout, and rates that do not divide a fixed refresh rate still face display quantization.

When demand temporarily exceeds the validated multiplier ceiling, the target clock retains less than one output of bounded credit instead of wrapping it away. This lets a source returning from an external throttle recover an achievable integer cadence without dropping generated work on ordinary timing jitter, while still preventing impossible whole-output debt from accumulating or producing later catch-up bursts.

The release-point cap has a separate queued-source qualification rule: it measures a complete eight-interval elapsed-time window, allowing short submissions and their compensating long GPU waits to contribute together. A long pause discards that window, and changing between released and ordinary delivery resets qualification. The measured throughput can lengthen output spacing below a nonbinding cap without moving the cap. A readiness miss skips an unacquired worker-copy generated image through its semaphore-protected continuation, while the real image remains deliverable. A generated image that was already presented retains its real output slot across joins. Overlap acquisition waits for one free image without draining future batches; [WSI isolation](WSI-ISOLATION.md#release-point-source-cap) owns the timeout and image-pressure details.

#### Integer pacing handoffs

Smooth Cadence may retain a delivery-validated integer multiplier. Fractional Adaptive normally retains its moving target clock, but an accepted constant cadence already replaces that clock with a fixed generated-frame count. Variable Fractional plans keep their target clock and do not request extra generated work. A FIFO handoff for an accepted constant cadence needs a confirmed compositor refresh match and is inactive natively.

Steady Adaptive's FIFO handoffs, a proven 2x cadence and a validated 3x–5x full-batch request, need a confirmed compositor refresh match. framegen-vulkan no longer reads compositor refresh feedback, so both are inactive natively and Steady keeps the target/multiplier base-cap ladder. Fixed's full-batch FIFO request has the same requirement. Explicit Fixed caps, Dynamic Cadence Recovery, transport recovery, and insufficient private-output capacity keep Fixed's normal budget policy.

framegen-vulkan does not read compositor VRR or refresh feedback, so no compositor state chooses an Adaptive multiplier, target, ceiling, or recovery, and no feedback change resets pacing helpers. Applied integer pacing separately verifies its measured workload cost, as described below. Allow Tearing is recorded but has no scheduling effect because the ordered SDR path deliberately owns FIFO.

#### Measuring applied integer pacing

For target-matched ordered Smooth Cadence with automatic integer pacing available, an accepted 3x–5x workload projecting at least 95% of target retains its adjacent lower-load baseline for at most eight seconds. If that same rung enters the fixed-refresh automatic target/multiplier cap during this window, framegen-vulkan discards the first interval, permits 250 ms of turnover, then measures at least one second of actual source intervals and completely delivered output counts. A later applied handoff starts its own bounded measurement without reusing the expired promotion baseline: after measuring the paced workload, it temporarily selects the adjacent lower workload through the existing efficiency-probe owner, applies the lower automatic cap, permits 250 ms of turnover, and obtains another continuous one-second delivered sample. Each sampling phase is bounded by eight seconds from its actual activation. Planned probe release and return remain one pacing lifetime until the same validated rung resumes, including when automatic-cap qualification takes longer than the 250 ms sample-settling interval. A workload/rung or pacing-owner change, timing reset, transport backoff, impossible fast burst or rescue invalidates that retained identity. Once the planned return completes, a later unrelated release must qualify a fresh comparison.

The lowest adjacent workload that measurably reaches at least 98% of target is preferred over a lower workload that misses that floor, provided its output gain clears the existing 2%-of-target margin. Intentional automatic target/multiplier pacing can therefore trade real-frame rate for the requested output: at a 120 FPS target, 54 real FPS at 2x supplies 108 output FPS, and settled 40 real FPS at 3x supplies 120 and is retained. If the lower workload already reaches the target, the higher workload cannot claim this preference. If the higher workload also misses the target, its output gain must still pay for the full real-FPS loss plus the margin; a 54-to-36 real-FPS change at 3x produces no gain over 108 and is rejected. The same comparison covers 3x–5x with no per-game or transport-specific thresholds. Delayed 16- and 27-second handoffs still require a fresh lower sample, so an old deficit cannot authorize extra work when the current lower workload already reaches the target. Accepted applied pacing reports `reason=settled-output-qualified`.

This follow-up check prevents another promotion or an independent lower-load efficiency probe until it resolves. Before integer pacing takes effect, a projected rate below 95% of target cancels the recent watch so useful 4x/5x qualification is not delayed by an unavailable pacing experiment. Constant-cadence qualification continues before the handoff so an uncapped Fractional plan can qualify; an active fresh comparison pauses it across both samples to preserve the planned pacing release. Quarter-second source windows in each measurement must remain within the existing 15% cadence envelope. Missing or partial generated delivery, an unexpected pacing-owner or rung change after sampling starts, timing/history reset, native rescue, impossible fast bursts, acquire backoff, changing source cadence, or expiration cancels incomplete evidence without rejecting the accepted workload. Interrupted fresh probes restore the retained workload through their existing owner. A measured rejection resets only transient constant-cadence state and the output clock, returns to the adjacent lower rung, and uses the ordinary 5/15/30/60-second retry ladder plus fresh lower-load qualification. Planned probe pauses and measured exits do not also start a separate 60-second handoff-failure cooldown, including uncapped Fractional comparisons. An expired baseline never acquires authority over a later scene. Manual and explicit Fractional priority caps, exact Fixed, 2x admission, unmatched targets, and Dynamic Cadence Recovery retain their existing policies. Requested timestamps and accepted output counts do not prove physical VRR scanout or input latency.

#### Adjacent-workload promotion

Every ordinary Adaptive promotion from 2x through 5x compares adjacent workloads. A current level that supplies at least 98% of the target does not probe a higher multiplier; a recovered source cancels a pending target deficit before promotion. Below that boundary, the ordinary one-second target-deficit guard remains in place and overlaps the lower-load qualification window. In both Steady and Fractional, a 3x–5x trial additionally requires two continuous seconds of fully delivered lower-load cadence within the existing 15% qualification envelope, measured in 250 ms windows of the canonical source estimate; recovering to the target cancels that candidate. Its highest sampled window rate supplies the adjacent-workload comparison baseline, so a brief low point cannot make extra GPU work look cheap. Initial native-to-2x admission retains its existing delay.

The higher load is accepted only when generated delivery is healthy and either its target-capped displayed-FPS gain pays for the real-FPS cost measured during the same bounded probe, or a 3x–5x trial closes a proven target deficit. Ordinary cost decisions retain their one-second trial. When only target preference can justify acceptance, the existing trial may extend by 250 ms for output-clock turnover before requiring at least one second of actual source intervals and accepted output averaging at least 98% of target, one delivery observation per interval, and complete generated delivery throughout the trial; a final smoothed-FPS estimate alone is insufficient. Missing observations, partial delivery, or bypassed intervals invalidate that preference without weakening the ordinary cost rule. Initial native-to-2x admission keeps its existing cost rule. Promotion to 3x–5x must additionally clear an output gain of at least 2% of the configured target; below-target trials must pay the real-FPS cost as well. This small margin rejects near break-even trades such as a 40-to-30 real-FPS drop for an 80-to-90 displayed-FPS gain at a 120 FPS target, while preserving the existing 2x admission rule. There are no multiplier-specific retention percentages, base-collapse boundaries, bridge probes, or 2x-only hitch exception.

A rejected level preserves its proven lower-load baseline through the bounded retry delay. After that delay, higher-level retries require either recovery to that baseline or two continuous seconds of fresh lower-load evidence within the existing 15% cadence qualification envelope. Every generated frame in the fresh sample must report complete delivery; missing observations, delivery pressure, timing resets, or a moving source restart qualification. Intentional Dynamic Cadence Recovery native samples pause the qualification clock and do not count toward its two seconds, so short probe intervals cannot indefinitely restart otherwise valid evidence. A fresh sample replaces the obsolete baseline with its highest observed window rate while preserving the failure count and increasing retry delays. The next actual trial still has to pass the same adjacent-workload and delivery checks; time alone cannot authorize promotion. After a rejected first 2x probe, native presentation may instead adopt a new gameplay baseline when the bounded cooldown has elapsed and output remains continuously below the near-target envelope for two seconds; retry delays back off from 15 to 30 and 60 seconds after repeated rejection. This prevents an ordinary scene change from leaving Adaptive permanently native-only without weakening the same-probe workload comparison. Later gameplay cadence cannot retroactively classify an accepted workload as a transport failure or authorize recreation; Adaptive's established cadence-rebasing policy remains feature-owned.

Lower-load Smooth Cadence efficiency probes retain their separate user-selected pacing behavior.

#### Automatic integer base caps

The fixed-refresh Adaptive 3x–5x base-cap policy requires one second at or above 95% of its selected cadence before entry. An active constant plan bounds the selected multiplier even when a higher workload remains validated: accepted 2x keeps the normal half-target cap, and a newly selected lower multiplier immediately releases any stricter old cap before qualifying its own. Without a constant plan, the validated workload still owns higher-rung qualification. An active cap tolerates dips down to 90%; a lower cadence or a return to the previous multiplier's range must persist for 250 ms before releasing it. This prevents entry-threshold jitter from repeatedly resetting the real-frame pacer. Transport guards, scheduler recovery, ramp evaluation, loss of eligibility and a return to 2x still restore normal pacing immediately; lower-load efficiency probes retain their separate cap transitions. The scheduler continues to require 500 ms continuously outside its useful retention range before releasing a qualified constant cadence. Transport, recovery, scheduler-probe, refresh-match and profile guards still exit immediately. Fixed's FIFO path has no automatic base-cap qualification or timed CPU sleep.

A fresh adjacent lower-load probe can release queued application returns when it lowers the automatic cap. Impossible fast intervals inside its existing 250 ms settling period remain real-only and are excluded, together with their following return interval, from measured workload evidence. They do not cancel and recursively restart the probe. The settling deadline is never extended; bursts after it expires, incomplete measured delivery, owner changes and transport recovery still invalidate the comparison.

#### Smooth Cadence rescue

`adaptive_auto_base_fps_cap` normally starts at half the target. Smooth Cadence rescue may release only this automatic cap during a one-second real-only pacing measurement; manual, explicit Fractional priority, and Fixed caps remain authoritative. A qualified Ordered-SDR cadence that exits its useful range retains its accepted baseline for at most two seconds: at least one second of actual source intervals must then show both a 22% source collapse and projected output at or below 80% of target before one rescue attempt starts. This catches gradual or bursty deterioration whose deepest sample comes after the cadence exit, without probing every low-FPS scene. The existing 15-second cooldown and requirement for a newly qualified stable cadence prevent repeated attempts in an unchanged heavy scene.

The rescue measures frame count divided by accumulated source interval time, discarding the first interval after a policy change. At the end of its one-second history-only measurement, it always restores the configured automatic cap and the previous generated workload, regardless of native headroom. A second one-second sample verifies recovery under that restored policy: at least eight source samples must recover 90% of the accepted baseline and improve 25% over the collapsed rate, with actual generated delivery and no missing or partial delivery observations. Planned output counts and generated delivery observations use bounded counters in the existing scheduler; no new polling, allocation or GPU query is needed. Native headroom is diagnostic information and cannot authorize a retained cap override. Ordinary higher-load trials wait until verification ends, then resume their existing qualification rules even when recovery failed.

Success, failure and interruption all leave the configured cap in force. Timing resets, hard cadence disruptions, impossible fast bursts, stabilization and generated-acquire backoff cancel an incomplete attempt; verification cancellation records its reason and cannot later commit stale evidence. A natural scene improvement can still coincide with the probe, but no outcome preserves a cap override beyond the native measurement. Expiration is consumed by the next scheduling call; a game that stops presenting receives no background recovery work. The existing cooldown and fresh stable-cadence qualification bound retries. The guard never changes saved settings, Steam hooks, Vulkan resources, swapchain lifetime or exact Fixed behavior. Diagnostics report `adaptive-rescue-start`, `adaptive-auto-base-cap-restored` with `reason=rescue-measurement-complete` before `adaptive-rescue-complete decision=verify-restored-policy`, then `restored-policy-recovered`, `restored-policy-not-recovered`, or an interruption reason. These observations report recovery under the configured policy, not the cause of the preceding slowdown.

Portable tests cover full-target capped recovery with and without native headroom at 90 and 120 FPS, persistent heavy scenes, natural scene recovery, a modeled feedback loop cleared by a brief reset, and a modeled slowdown that would need continuous uncapping. Five-minute continuations apply the production cap owner and require the configured cap outside the native measurement in every scenario. Additional regressions cover repeated collapses, missing and partial generated delivery, brief headroom, ordinary short dips at 60/90/120 FPS, and interruptions in both measurement and verification. Manual and explicit Fractional caps, Fixed isolation and live policy transitions retain their existing contract tests. These simulations do not establish a real-game false-positive rate or prove resolution of a Steam Deck long-session stall.

#### Lower-load probe retries

An ordinary lower-load Smooth Cadence probe keeps the proven higher rung while testing the cheaper workload. Its initial 250 ms check, with one optional 250 ms settling extension, can reject an insufficient workload but cannot alone accept it. A promising result must then sustain at least one second of raw source intervals with one complete generated-delivery observation per interval, and both its measured average and final cadence estimate must reach 98% of target. Missing, partial or duplicate delivery, native bypass, acquire backoff, or a timing reset prevents incomplete evidence from accepting the downshift. This avoids retaining a briefly fast 2x workload that settles below target after queued work drains; sustained target-capable 2x remains eligible. The counters belong to the existing scheduler and add no GPU work, allocations or polling. Separate applied-integer-pacing comparisons retain their own continuous measurement owner.

Rejected lower-load Smooth Cadence probes retain their 60-, 120-, or 300-second retry deadlines independently for each tested multiplier. Cadence loss, stalls, and transport history refreshes preserve completed rejections without extending their deadlines; timing resets discard only an incomplete probe's evaluation. Requalifying the same cadence therefore cannot repeatedly restart an unsuccessful downshift. A different multiplier remains eligible for its own experiment, and independently observed source improvement can still qualify a useful lower cadence. Confirmed Dynamic Cadence Recovery, qualified near-target native preference, or a newly constructed scheduler clears obsolete rejection history. This applies to Steady and Fractional Adaptive probes from 3×→2×, 4×→3×, and 5×→4×; Fixed and 2×→native planning do not use this efficiency-probe policy.

#### Bursty source cadence

A transient source-rate burst above the larger of three times baseline or twice target is treated as native activity and does not advance policy clocks.

Cadence-drop detection holds the proven interval while confirming three consecutive samples at least twice as long. It also accumulates those candidate samples in a shadow smoothed estimate: if the next sample rejects the sustained-drop hypothesis, the estimator incorporates the delayed observations before the current interval. Discarding them instead can lock onto only the fast half of a bursty stream, for example reporting 125 FPS for alternating 8/32 ms intervals whose actual rate is 50 FPS, and suppress useful generated work. Timing resets, impossible fast bursts, and transport backoff discard pending drop evidence. The existing hard-stall, history, delivery, and multiplier bounds still apply. Portable tests cover both recovery policies and Smooth Cadence settings. They are source-cadence evidence, not a simulation of HID polling, game input, or physical scanout.

### Dynamic Cadence Recovery

Dynamic Cadence Recovery is an optional per-profile policy for games or emulators that switch native rates. Ordered FIFO can make a native 60 FPS mode look like 30 FPS when generation is active, so framegen-vulkan periodically requests a native-only sample. When framegen-vulkan owns an output timeline, the presentation owner supplies its already-scheduled deadline. A native probe captures that horizon once, discards intervals before it and the interval crossing it, then starts its cadence measurement. New native-only outputs cannot extend that captured horizon. An ignored fast-burst interval can finish this drain when it reaches the horizon, but cannot count as a recovery confirmation; the next complete post-drain interval is measured normally. This uses existing CPU timing metadata and adds no GPU wait, query, guessed drain duration or transport polling; unbridged probes retain their immediate measurement. Three consecutive samples at least 25% faster than the captured baseline confirm the new cadence. If that sample reaches the native-preference envelope, the probe keeps generation paused through the existing one-second quality qualification, including a first sample at or above target followed by cadence slightly below it. After confirmation, that opt-in native measurement counts all source intervals in bounded quarter-second windows, including queued bursts, and uses their frame-count/time rate for native-preference qualification and retention. A single late turnover frame must not immediately cancel the measurement or bias it toward only the slower half of a bursty native stream. The existing 95% output floor, interval-quality comparison and one-second qualification remain authoritative; a below-floor measured window cancels qualification. Timing resets discard the measurement, and an intervening generated-image recovery probe also restarts native confirmation and its normal retry interval, so samples on opposite sides cannot masquerade as consecutive native frames. Ordinary source estimation, promotion evidence, recovery-disabled behavior and Fixed retain their existing policies. Sparse generated FIFO work must not contaminate that native measurement and hide the recovered rate again. A loss of qualifying cadence cancels the measurement and restores ordinary planning; Fixed recovery does not use native-preference qualification; Adaptive keeps its existing stable-cadence and recovery guards.

Adaptive keeps its configured target and ceiling. Fixed would use a confirmed compositor refresh as its target and treat its multiplier as a ceiling, but framegen-vulkan no longer reads compositor refresh, so Fixed stays exact Fixed. Enabling recovery disables manual and automatic base caps.

## Transport recovery

Fixed ordered generated-image acquisition uses one application-present deadline, not a refresh-derived slow-call threshold per generated image. Each image receives only the remaining cumulative configured budget. An unconfigured Fixed path with relief headroom retains its unbounded compatibility contract. When the image pool fits the Fixed batch but lacks an additional relief image, the shared deadline is at most 50 ms; a shorter configured deadline wins. Headroom-tight admission remains nonblocking. Normal Adaptive ordered delivery preserves the established sequential FIFO acquisition point. Fixed refresh retains the configured sequential acquire contract from 3.3. Returned image count and batch size determine the turnover proof, independently of refresh rate, source FPS, device identity, or a timer.

A `VK_TIMEOUT`/`VK_NOT_READY` result, exhaustion of the configured cumulative acquire budget, or completion of an ordered batch after that cumulative wall-clock budget has been reached starts blocking ordered transport recovery. The deadline is the explicit application-present budget; it is not derived from output FPS, GPU load, device, resolution, or post-processing cost. Fixed-refresh Adaptive and direct Fixed deadline failures enter the ordered native-drain retry ladder of 250 ms, 500 ms, one, two, five, 15, and 30 seconds. Recovery probes retry one image using the explicit configured acquire budget or one confirmed display period, and without either contract the retry is nonblocking. There is no FPS-derived acquire deadline, native-cadence hold, repeated-episode counter, failure-count-derived acquire timeout, or timed recovery window.

An explicit live generation-policy transition arms one one-shot recreation permission. Multiple policy writes before the transition is applied are last-value-wins: generation remains suspended, the scheduler is reconstructed once from the final values, and that transition owns the single transport permission. The first generated-image acquire batch completed within its configured budget consumes the permission without action. If an acquire timeout, budget exhaustion, or cumulative deadline overrun occurs first, one successful retirement-protected real present may request a game-owned recreation; the context cannot signal it twice, and a replacement context initializes from the current transition sequence so the same old event cannot rearm a loop. Fixed direct deadline failures retain bounded in-place backoff.

A recovery probe runs only when temporal history is ready and the current Fixed or Adaptive policy requests generated work. A real-only policy frame performs no generated-image acquisition and leaves the pending probe intact for the next eligible frame; it cannot count as a probe failure or increase recovery backoff.

Lower `QueuePresentKHR` duration is diagnostic only. A successful but slow present cannot quarantine generation, change a multiplier, warm history, or request recreation. framegen-vulkan cannot reliably distinguish compositor throttling, stacked GPU work, VRR behavior, or a game-scene change from a wedged queue by elapsed time alone.

Cadence stalls and low FPS never request swapchain recreation. Live Fixed/Adaptive mode, multiplier, base-cap, target, Smooth Cadence, and Dynamic Cadence Recovery changes apply a transient boundary: incomplete ordered-acquire retry state is discarded, history restarts from three frames, and the one-shot direct-failure permission is armed. Fixed never launches a cadence-collapse probe: its user-selected multiplier remains exact unless a direct Vulkan failure owns bounded transport safety.

Pacing history preserves failure counts and remaining cooldowns for rejected native-to-2x and higher-multiplier trials. After cooldown, fresh source and lower-load evidence are still required; elapsed time cannot qualify a retry. Explicit policy resets discard this history.

After a Fractional/Steady recovery event, history warm-up and scheduler planning use the same source-cadence boundary: the application-present start after real-frame pacing, or the reserved cap deadline when a capped plan prepares during that wait. Backend scheduling and GPU waits must not move that event-recovery clock forward within the frame: doing so seeds cadence from only the remaining fraction of a frame and can repeatedly mistake a steady source for a cadence drop. Ordinary generated-image timeout recovery deliberately retains the 3.3 completion boundary, preventing recovery work from being reinterpreted as new gameplay cadence. This applies to Adaptive and Fixed + Dynamic Cadence Recovery; exact Fixed has no scheduler cadence history. Portable recovery coverage models 12 ms of private work inside steady 60 FPS event-recovery frames; hardware recovery and external-overlay suites must still prove resumed delivery.

`GeneratedDeliveryWindow` compares requested outputs with outputs queued inside framegen-vulkan's budget. It does not claim compositor scanout. Diagnostics distinguish requested, admitted, scheduled, and delivered counts.

Private Flow Scale, model, or generated-capacity changes retain the old policy while replacement resources are prepared. Capacity growth that does not fit the current WSI pool remains pending for game-owned recreation. [Runtime configuration transitions](RUNTIME-TRANSITIONS.md) owns that lifecycle. Ultra Performance is a restart-bound resource policy, not a separate scheduler.

## Runtime validation

The external-recovery inventory pairs unidentified-overlay controls across Adaptive 2x and 3x, Fixed, and Frame Generation-only operation. Pause, covered-throttle, and repeated short/long journeys must independently prove source recovery, target-output recovery, focus sequencing, fresh history, generation suspension where applicable, and context stability. Portable policy tests separately cover Fractional/Smooth mode, automatic base-cap state, 2x–5x ceilings, failed-baseline retention, exact Fixed stability, transition-scoped acquire failure, inert successful transport, and the absence of FPS-authorized recovery so hardware rows do not carry the full combinatorial burden.

For affected changes, cover these runtime boundaries:

| Boundary | Minimum evidence |
| --- | --- |
| Generation modes | Live `0x`, Fixed 2x and affected higher multipliers, Fractional Adaptive, Smooth Cadence, and unreachable targets. |
| Cadence changes | Startup, gameplay rate changes, true fixed-rate rejection, short hitches, long interruptions, and fast-present bursts. |
| Presentation | Ordered SDR, explicit acquire failure, configured cumulative acquire-deadline overrun, slow lower-present non-authority, focus and overlays, resize, recreation, and shutdown. |

| Quality/performance | Real FPS, displayed FPS, frame-time percentiles, generated share, visible artifacts, latency impression, GPU time, and memory where relevant. |

Record the commit and build identity, hardware, driver, compositor, runtime, game and resolution, policy settings, transitions, diagnostic path, and verdict. Mark unavailable hardware or paths **not tested**.

Presentation diagnostics are opt-in and can perturb pacing. Use `adaptive`, `recovery`, and `performance` presets for a separate diagnostic run, then disable them for subjective comparison. Their timestamps describe framegen-vulkan policy and queueing, not compositor scanout.

## Release gates

An affected candidate is ready for broader testing when:

1. portable and sanitizer policy tests pass;
2. affected Fixed and Adaptive modes stay within their ceilings;

## Native Fixed output handoff validation

An admitted native detached Fixed worker can qualify ready-output spacing with Smooth Cadence off whether the configured source cap is zero, binding or nonbinding. Cap-owned preparation and release-gated scheduling retain precedence over the ordinary ready fallback. The `profile-update` regression combines actual eligibility and the canonical pacer for caps 0, 610 and 60 across 60 → 30 → 100 → 30 FPS sources, checking half-source-period slots after qualification, no source hold from nonbinding caps, and binding-cap takeover/release. Timing owners, recovery, serialized completion pacing, Adaptive and disabled generation retain their exclusions. This changes no saved cap value or cap semantics.

Native Fixed's bounded output handoff is specified in [WSI isolation](WSI-ISOLATION.md). Its `deferred-present` portable test covers copied inputs and retirement fences, one-slot admission, acquire-style polls/timeouts, actual error retention, repeated handoff, worker teardown and shared private-queue serialization. Queue-reservation tests preserve caller storage and indices, reject protected queues and account for all requests against physical family capacity. Scheduling estimators and readiness-before-spacing remain owned by `RealFramePacer`; the worker delivers only the current bounded native output batch. Qualify early versus late acquisition, game CPU load, pipeline acquisition, mode changes, replacement, idle/destruction and driver errors on hardware.


An actually queued native real output supplies detached-output evidence for the next source observation. Across a complete eight-sample detached window, the pacer updates the full-source median in either direction while retaining output spacing. Paired early/late arrivals and short acquisition joins must not enter the synchronous two-faster-sample release path or trigger eight unpaced batches; a one-way minimum must not ratchet the interval toward faster jitter. Acquisition waits remain measured source-wait cost, but do not change how the preceding output was submitted. Two consecutive full intervals at least one quarter shorter retune large recovery debt; four consecutive faster samples using the existing full-interval and wait-excluded work tests retune smaller sustained improvements. Detached acceleration shortens the interval in place without clearing the qualified period or discarding the source window. Its slower samples still correct an early-arrival estimate. Longer runs of early arrivals can pass a consecutive-sample threshold without a genuine mean-rate change, so no such threshold may create eight unpaced batches. Synchronous delivery retains its release-and-requalify rule because its output sleeps can hide the source cadence. Merely having a private queue or an idle worker does not supply detached evidence. `testDetachedOutputSourceJitter` checks balanced 60 FPS jitter with runs of two, four, six and sixteen early/late intervals and brief acquisition joins, genuine faster/slower 70/80 FPS changes, sustained slower arrivals and repeated workload recovery with actual detached-slot acquisition feedback, including 8 ms readiness that conceals a smaller speedup.

A readiness miss must not erase an established detached cadence episode. An underestimated interval can make preparation exceed its budget; treating that unpaced batch as synchronous removes the slower-window correction and can cause repeated qualification gaps. `testDetachedCadenceAfterReadinessMiss` feeds four early and four compensating late source arrivals through actual bounded readiness decisions, requires recovery to the original spacing, and limits cascading misses. A synchronous paced batch or policy reset ends the episode.

Native Fixed 2x cap-owned batches on the same eligible private-queue path also establish backend readiness on the worker within one full source period from arrival, bounded at 50 ms. A first-slot miss before that deadline moves the output phase later without shortening output intervals or moving the application source-cap clock; final real delivery uses the existing bounded handoff. The worker retains at most one source batch; it never queues a second batch to recover output debt. `testLateNativeFixedCapKeepsSpacing` checks late preparation, complete within/between-batch spacing, unchanged source-cap deadlines, rejection of whole-period debt, and isolation from Adaptive target clocks. A short source-cap miss may use the ready fallback only after actual detached delivery has established its cadence episode; private queue availability alone cannot authorize that wait. Long source interruptions still skip it. Eight consecutive slower detached arrivals without another cap-paced batch release cap ownership without discarding the learned period. `testDetachedCapYieldsToGameLimiter` covers the transition from a 70 FPS framegen-vulkan cap to a 60 FPS game limiter. GPU timeout and other transports retain their existing fallback. This adds no worker, queued image, allocation, query or presentation extension.

Detached ready batches retain one output phase across source boundaries. The next first slot follows the previous real slot, rebased from the worker’s actual lower-call start when delivery is more than half a slot late. Ordinary wake lateness stays on the absolute phase rather than extending every period. Early readiness may reserve less than one additional output interval; it never makes the game thread wait for that first slot. Exhausting that bound releases only the cross-batch phase for two observation windows, ensuring one complete eight-sample window without phase holds at any window alignment while preserving within-batch spacing and the qualified source estimator. Two samples of improved wait-excluded work hidden by measured acquisition joins and a preceding first-slot hold can release the same phase; GPU-readiness changes alone cannot. Missing or synchronous delivery, count/owner changes, policy reset and errors discard the ready phase; cap-owned and compositor clocks retain their existing owners. `testDetachedBatchPhaseContinuity` exercises steady source intervals, alternating 4/7 ms readiness, uncapped entry and a late worker wake across 2x–5x, checking every boundary rather than only batch intervals. `testDetachedBatchPhaseRecovery` feeds relative and absolute producer limits through readiness, complete-batch retention and acquisition joins, requiring recovery from 20 to 40 FPS and back without an old-phase throughput lock. `testDetachedBatchWakeFeedback` additionally feeds 2,400 source frames through pending GPU work, acquisition joins and repeated 100 µs worker lateness, requiring stable learned intervals and source throughput. These are deterministic scheduling checks, not displayed-motion evidence.
