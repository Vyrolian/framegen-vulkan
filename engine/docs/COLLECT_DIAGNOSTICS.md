# Collect framegen-vulkan Diagnostics

For installations using `fgvk`.

## 1. Enable logs

Fully close the game and save its current launch settings so you can restore them afterward.

**Steam or Proton:** prepend the two diagnostics variables to your existing Launch Options, preserving any profile, shader, or other settings. For a basic launch, the result is:

```text
FGVK_PRESENT_DIAGNOSTICS=1 FGVK_PRESENT_DIAGNOSTICS_THRESHOLD_MS=25 ~/.local/bin/fgvk %command%
```

For a system installation, use your normal `fgvk` path.

**Heroic, Lutris or Flatpak:** keep your working setup and add these per-game environment variables:

```text
FGVK_PRESENT_DIAGNOSTICS=1
FGVK_PRESENT_DIAGNOSTICS_THRESHOLD_MS=25
```

**Terminal launch:** capture the game output:

```bash
FGVK_PRESENT_DIAGNOSTICS=1 FGVK_PRESENT_DIAGNOSTICS_THRESHOLD_MS=25 \
    fgvk your-game-command 2>&1 | tee "$HOME/Desktop/framegen-vulkan-renderer-session.log"
```

Replace `your-game-command` with your normal game command.

## 2. Reproduce the problem

Start the game, reproduce the issue once, note what happened and fully exit. Collect the report before another test run.

## 3. Save the report

In Desktop Mode, open Konsole and run:

```bash
fgvk-diagnostics --lines 5000 all > "$HOME/Desktop/framegen-vulkan-diagnostics.txt" 2>&1
```

If the command is not found, try `~/.local/bin/fgvk-diagnostics` instead. For the terminal capture above, add `--log "$HOME/Desktop/framegen-vulkan-renderer-session.log"` before `--lines`.

The file appears on your Desktop; Konsole normally prints nothing. If no log is found, check the temporary launch settings and repeat the test.

For a slowdown after a long session, replace `--lines 5000` with `--lines 200000`. Collect before starting another game.

Collect from the original session log, not an older filtered report, which may have omitted error details. The report does not include the separate Gamescope system journal; support may request it if the game log is insufficient.

For comparisons, collect a separate report after each run and note which settings changed. Use the same scene and game settings where possible. For HDR sharpening comparisons, also note the game resolution and display resolution. For VRR comparisons, record the VRR setting, display refresh rate, desktop or Gaming Mode session, and Gamescope version if used.

For timing-field meanings and the limits of log-based comparisons, see [Interpreting presentation records](WSI-ISOLATION.md#interpreting-presentation-records).

## 4. Restore your settings

Restore the original launch settings and remove the two temporary diagnostics variables.

## 5. Send the report

Review `framegen-vulkan-diagnostics.txt` and remove personal information. Upload it through the [diagnostic form](https://docs.google.com/forms/d/e/1FAIpQLScSd9qgkYCq3Kbbc3_52k4_82iTmEqt3_FxOqGuxQ6FsjutgA/viewform), choosing **framegen-vulkan (standalone/direct installation)**. Answer **Unknown** when unsure. Do not post the log publicly or attach `Lossless.dll`.

## Compare framegen-vulkan and NVIDIA Smooth Motion without Nsight

The source-checkout tool [`profile-framegen.py`](../scripts/profile-framegen.py) captures GPU board telemetry and configures MangoHud CSV logging around your existing launch command. It uses Python's standard library, your installed `nvidia-smi`, and your existing MangoHud wrapper. It does not inject another profiling layer, run Nsight, change saved profiles, select a cap, override Reflex or VSync, or rebuild/install the Renderer. CPU/GPU/protocol/content framegen-vulkan profiling flags are set to 0 in the child, so detailed tracing cannot force the overlap rings to drain.

Use `--manual` for button-controlled recording: load the game and reach the scene, press **Left Shift + F2** to start, then press **Left Shift + F2** again to stop. GPU sampling starts only when the connected MangoHud process opens its recording CSV, and stops on that process's `LoggingFinished` control event. There is no startup countdown or seconds to track. `--buttons` optionally adds a small Start/Stop window using the host's optional Python tkinter module; closing that window leaves the in-game key available. The control connection uses a unique per-launch abstract Unix socket and verifies its same-user process and open CSV before starting GPU sampling. Control loss or game exit without a stop event leaves the recording explicitly incomplete. A recording is bounded to ten minutes; the tool requests a stop at that limit and marks a missing acknowledgement incomplete.

Manual runs create a new private `session-*` beneath the requested folder, so `mako-profile` and `smooth-motion-profile` can be reused without overwriting earlier captures. On stop, the completed CSV is frozen separately under `recorded/` and the report is saved while the game stays open; later MangoHud recordings cannot change that report. Exit the game normally to finalize its exit-status metadata. The two named recording folders are ignored by Git when kept in the framegen-vulkan checkout. The comparison command accepts either session directories or the parent folders, selecting and printing the latest saved session report for each parent.

For the framegen-vulkan run, prefix the existing game launch command, keeping MangoHud and your working launcher arguments. For example, with a standalone installation:

```bash
python3 /absolute/path/to/framegen-vulkan/engine/scripts/profile-framegen.py capture \
  --mode fgvk --scenario cyberpunk-scene-A-60fps --reflex on \
  --manual --output ./mako-profile \
  -- mangohud ~/.local/bin/fgvk /path/to/game
```

For Steam, replace `/path/to/game` with `%command%` in Launch Options. If your command already includes `mangohud`, keep that single wrapper. Do not add a second one. Preserve required game/Proton environment and working launcher arguments; a downstream script that resets the environment can override these requested settings. A wrapper that detaches the game and exits immediately produces an incomplete run; use a command that stays alive with the game. Flatpak sandbox admission and output-directory access are not prepared by this tool.

For baseline and Smooth Motion, run the game with MangoHud directly, outside `fgvk`. framegen-vulkan's launchers deliberately isolate implicit-layer discovery and can suppress MangoHud when framegen-vulkan is disabled, so wrapping those launchers would not provide a valid shared observer. The profiler refuses those known combinations and refuses an inherited `VK_IMPLICIT_LAYER_PATH` override for Smooth Motion. For example:

```bash
python3 /absolute/path/to/framegen-vulkan/engine/scripts/profile-framegen.py capture \
  --mode smooth-motion --scenario cyberpunk-scene-A-60fps --reflex on \
  --manual --output ./smooth-motion-profile \
  -- mangohud /path/to/game
```

Use `--mode baseline --manual --output /path/to/baseline-profile` with that same direct game command for the control. In Steam, keep `%command%` and any required Proton environment, replacing only the framegen-vulkan activation wrapper. Resolve relative output folders against the launcher's working directory, or use absolute paths to keep recordings in the framegen-vulkan checkout. Do not change the working saved launch option until you have retained a copy. framegen-vulkan-only launcher compatibility settings are not reproduced in direct runs; record required equivalents explicitly rather than assuming those environments match.

Capture three separate launches with `--mode baseline`, `--mode fgvk` and `--mode smooth-motion`. Baseline disables both framegen-vulkan layer roles and NVIDIA Smooth Motion. Smooth Motion enables `NVPRESENT_ENABLE_SMOOTH_MOTION=1` and disables both framegen-vulkan roles. framegen-vulkan enables its Renderer layer and disables Smooth Motion; configure Fixed 2x in the existing profile yourself. Non-framegen-vulkan modes remove explicit framegen-vulkan entries from inherited `VK_INSTANCE_LAYERS` without changing other layer order. These are requested activation settings, not proof that the intended game loaded a layer or actually generated frames. Verify activation separately. Existing shader/scaling settings can make the comparison unequal; hold those constant and record them in the scenario label.

Keep the same game-side source cap, graphics settings, camera/scene, power mode, presentation mode and Reflex state. Start with 60 source FPS, then repeat under GPU saturation for throughput loss. Repeat each configuration at least three times and alternate order. `--reflex` records a label without changing the game. `--gpu` selects one NVIDIA index or UUID; default is index 0. `NVPRESENT_QUEUE_FAMILY` and MangoHud's existing limiter/settings are preserved. NVIDIA documents that selecting graphics queue family 1 for overlay compatibility can reduce performance; record that choice and do not silently compare different queue settings.

The default sampler queries power, GPU utilization, board VRAM, graphics/memory clocks and temperature every 500 ms using one persistent `nvidia-smi` process. Missing sensors remain unavailable. Board telemetry includes the compositor and other processes; it does not isolate frame-generation execution time. Energy integrates only adjacent valid power samples with gaps of at most two seconds and reports its covered time separately. Without `--manual`, the original timed mode remains available: GPU sampling stops after the requested `--warmup` plus `--duration` without stopping the game, each bound at most 600 seconds, and the output directory must be new. Captures contain `metadata.json`, `telemetry.jsonl`, `report.json`, `report.txt` and MangoHud files. Launch metadata excludes the full command and environment; raw MangoHud logs still contain system/program information. Each new session directory is private (0700); tool-written files are 0600. Captures stay local and nothing is uploaded or archived automatically.

In manual mode, boundary uncertainty includes control dispatch, CSV observation and polling (normally up to 100 ms plus scheduling/I/O delay); these are host observations rather than exact GPU boundaries. In timed mode, MangoHud logging starts after its own initialization plus `--warmup`, whereas telemetry warmup starts at launcher entry, so those windows are not exactly aligned. Default `--frame-log-interval 0` logs every frame observed by MangoHud, with CSV-write overhead. A positive interval in milliseconds reduces logging frequency but samples individual frame times; the report then withholds derived FPS and labels its quantiles as sampled observations. Logging controls are child-only overrides appended to the existing inline MangoHud settings; file-based configuration remains available through `read_cfg` when no inline configuration existed. Logging/upload settings are overridden, while your existing wrapper, config path, HUD and limiter options are retained. Logging overhead must be qualified with matched off/on runs before calling it negligible.

```bash
python3 engine/scripts/profile-framegen.py compare ./mako-profile ./smooth-motion-profile
```

The comparison reports power/load/memory and each MangoHud stream's frame-time distribution separately, warning about mismatched scenario, Reflex, GPU, window and sampling labels. It never merges launcher/game logs. MangoHud layer order can put its counter before or after generation, so frame domain defaults to `unknown`; use `--frame-domain source` or `output` only after independently verifying that boundary for that launch. Output FPS cannot establish real-source throughput loss, actual scanout cadence or generated-frame acceptance. Frame time is not input latency. These captures explicitly leave input-to-display latency and GPU execution milliseconds unavailable; they cannot establish either implementation's latency advantage. This shared sampler replaces neither framegen-vulkan's detailed attribution tools nor a physical input-latency measurement.

## GPU Headroom evidence

Reports retain Headroom cap changes and any Adaptive efficiency trial cancelled because the cap made its output target unreachable. A cancellation restores the proven workload and is not a presentation failure.

Compare the same scene with GPU Headroom Off and On. Collect a report after each run and note the reserve, Fixed/Adaptive mode, multiplier ceiling and any game FPS cap. Brief utilization spikes can still reach 100%; the readings cover the whole GPU and do not measure per-game GPU time or power. See [presentation records](WSI-ISOLATION.md#interpreting-presentation-records) for the retained fields and controller states.

## Detailed game frame trace

For a supporting local Renderer build, prepend `FGVK_PACING_PROFILE_TRACE=1` to the existing game launch command, preserving its arguments and graphics settings. After the process exits, retain the raw private capture path printed by framegen-vulkan; filtering or tailing a long capture can remove frame identities needed for exact joins.

`FGVK_PACING_PROFILE_TRACE=1` enables a detailed game trace with the CPU, backend GPU and native Wayland observers together. Each `pacing-profile-source` record retains its own source ordinal, CPU entry/exit, effective settings, cap/readiness/output waits and private phases. `pacing-profile-application` records retain every outer present/acquire call, thread/stream ordinal, successful acquired image, and separate known/unavailable configuration and pre-configuration join durations; managed presents carry the exact source/context identity. `pacing-profile-wait` retains individual wait1/wait2 calls, including sessions shorter than one second. Version-2 output records additionally retain worker enqueue, queue-lock and actual existing readiness-wait timestamps/results. They are published when the producer collects a completion, without waiting for a summary window. No additional GPU wait or pre-present fence query is introduced. Existing full-trace mode also records each actual lower acquire attempt as `pacing-profile-acquire-driver`, including its unmodified timeout/result and a unique outer acquisition ID. The outer acquire records its context lifetime and summed driver-call time; the remainder is framegen-vulkan/observer CPU time, not an inferred GPU wait. Present records include the actual returned Vulkan result and caller queue. Native unscaled FG source/generated copies emit `pacing-profile-copy` submission records with source/image identity, queue/device/command/fence handles, binary wait/signal lists (up to 16 each, with original and retained counts), timeline dependencies and submission-call boundaries. The trace writes these submission records; their GPU timestamp companions, described below, need `FGVK_PACING_PROFILE_COPY=1`. A thrown submission is explicitly unsuccessful and still propagates unchanged. Detailed output records identify their actual lower queue and binary wait. These are submission dependencies, not game simulation timestamps, application rendering submissions or per-image GPU completion.

`FGVK_PACING_PROFILE_COPY=1` implies the trace and also timestamps native unscaled source and generated copies on the application device. One bounded query pool records top/bottom timestamps in the existing copy command buffers; no presentation wait or extra queue submission is added. Results are read without `WAIT_BIT` only after the existing final-copy fence proves that batch complete. `pacing-profile-copy-gpu` retains exact process/context/source/resource-generation, image/command/queue identities, raw GPU ticks, valid bits and timestamp period, query availability/result, read cost and separate before/after device-to-host calibrations with their maximum deviation and CPU call bounds. The optional supported `VK_KHR_calibrated_timestamps` or `VK_EXT_calibrated_timestamps` extension is negotiated only with `FGVK_PACING_PROFILE_COPY=1`; no feature is enabled. Unsupported domains retain raw durations without host-clock mapping. `pacing-profile-copy-gpu-state` reports initialization and calibration availability. Timestamp writes and calibration have diagnostic cost; this mode is not a zero-overhead observation. It also moves generated copies onto the application's present thread with fence-based render-slot admission, so its pacing is not the product's.

The reader joins a native GPU sample only to the matching submitted copy in that resource generation, then compares its calibrated end-time estimate with the matching actual lower-call entry. It uses the exact existing Wayland call boundary when uniquely recorded; otherwise it keeps the whole output scope as entry uncertainty, including possible queue locking and observer setup. It retains both calibrations and an uncertainty interval including their error and disagreement; narrow counters, stale/wrong clocks, missing queries, duplicate slots and mismatched identities remain unavailable. Reports separate before/after/ambiguous estimates, missing completion samples and measured query/calibration CPU cost. A source-copy timestamp describes framegen-vulkan's copy after its upstream semaphore wait, not the game's simulation timestamp. A copy-end marker precedes the later WSI semaphore signal; neither the marker nor clock calibration measures that signal or physical scanout. Shutdown tails can lack a completion sample because tracing never adds a drain solely to flush evidence.

Compare selected good and bad portions of an existing capture with the repeatable `--presentation-window START:END` option; offsets are seconds from the first uniquely requested/presented feedback on each process/surface/clock/output, preserved across swapchain contexts. For example:

```bash
python3 engine/scripts/analyze-pacing-profile.py /path/to/fgvk-pacing.log --top 3 --presentation-window 90:95 --presentation-window 95:100
```

The comparison keeps contexts separate and requires unique feedback requests, successful lower calls and matching output identities. It reports CPU entry/return, requested deadline and compositor gap distributions for the same consecutive output pairs, role-specific presentation gaps, and calibrated copy completion relative to exact lower entry. Missing, duplicate, discarded, backwards or discontinuous associations cannot produce a paired interval. Nominal deadline drift against reported refresh multiples is separate from measured vblank phase and cannot establish causality. A feedback-to-output join still needs the protocol companion to verify its buffer commit; these measurements do not inspect pixels. This option analyzes existing files and adds no capture overhead.

`pacing-profile-gpu` retains each completed backend batch's durations and its exact source, backend frame and resource-generation identity. The bounded eight-entry source map rejects overwritten identities; resource replacement clears the map and advances its generation. Missing completion samples, history-only turns, shutdown tails and ambiguous matches remain unavailable. GPU durations cannot establish host-clock readiness or game simulation time. The session's `renderer_build_id` identifies the mapped ELF image even when an incremental-build fingerprint is stale, and process/profile identity is copied into the private capture. Timing captures contain these framegen-vulkan identity records, not arbitrary game output.

The full trace preserves its beginning up to 64 MiB and stops explicitly at the limit. It adds per-call formatting/file publication as well as GPU/protocol observation overhead; use it for focused investigation and remove the flag afterward. It does not change saved profiles or pacing. From the source checkout, `python3 engine/scripts/analyze-pacing-profile.py /path/to/fgvk-pacing.log --frames-json /absolute/new-frames.json` exports a private per-source timeline with exact application/GPU/output/Wayland joins, omitted-record markers and unmeasured boundaries. Existing output files are refused. The text report prints the worst source gaps with outer-entry/outside-application time, current join/waits and the matching GPU span; older captures remain readable without inventing this evidence. For exact driver buffer/commit correlation, add `--frame-trace` before `--` in the existing `wayland_pacing_protocol.py` companion command below. That companion preserves the existing launch arguments and enables the flag only in its child. The export additionally links each successful application acquisition to its corresponding presented image within the same process/context/swapchain lifetime. It consumes that ownership once, preserves failed/unmatched acquisitions and copy records, and declines exact ownership joins across omitted, malformed or rolled-over data. Driver attempts are partitioned only when counts, ordinals, intervals and summed durations agree. No new flag is needed. Pictures still require the separate explicit content trigger.

The companion also reports a separate comparison between consecutive buffer attachments. It accepts extra commits between their exact feedback-associated commits only when both endpoints attach a non-null buffer, no other attach request occurs between them, feedback ordinals are consecutive and the source context is unchanged. Reattachment of the same buffer and null attachments count as intervening attachments and reject the pair. Malformed/conflicting protocol evidence disables this supplementary comparison. Strict adjacent-commit results remain separate. This covers observed WSI FIFO-state commits without assuming they submit another picture or hiding intermediate buffer submissions; protocol marshalling still does not prove compositor receipt or scanout.

### Vulkan setup comparisons

To compare a game with a synthetic reproducer, full trace also records `pacing-profile-vulkan-setup` version 1 at instance/device/surface/swapchain creation. Each create attempt pairs the incoming request at this framegen-vulkan layer boundary with the forwarded request and actual lower result, including retries. Records retain enabled extension names, API version, surface entrypoint, requested queue family/count/flags, swapchain geometry/format/usage/mode/image minimum and bounded `pNext` type lists. Selected presentation/descriptor-heap feature values are decoded; other feature payloads are unavailable. Lists stop at 256 extensions, 256 chain nodes and 64 queue requests with explicit truncation. This adds no Vulkan queries and no per-frame observation. Enabled features and types do not prove actual use; use the individual wait and output records for that distinction.

Run `python3 engine/scripts/analyze-vulkan-setup.py /path/to/game-pacing.log --compare /path/to/tester-pacing.log` to inspect setup differences as JSON. Select `--pid` and `--other-pid` when files contain several processes. The reader selects the last successful lower swapchain and its preceding device within one PID/layer role; verify that this is the gameplay surface. Original handles remain in each inventory but are excluded from cross-run equality. Missing old setup, partial pairs and truncated extension lists remain unavailable; failed creates cannot replace a successful selection. Equal recorded setup is not a reproduced presentation fault. Retain the raw histories and compare matched settings and actual call/commit/presentation intervals as well.

The Wayland companion's optional `--runtime-log /absolute/new-runtime.log` enables `VKD3D_DEBUG=info` and `DXVK_LOG_LEVEL=info` only in its child, saves matching framegen-vulkan/DXVK/VKD3D diagnostics and selected launch-environment fields to a new mode-0600 file, and stops at 4 MiB with a marker. It keeps other stderr passing through and excludes Wayland input traffic. Use it with `--frame-trace`; runtime redirection by a launcher or an existing `VKD3D_LOG_FILE` can leave coverage incomplete. Retain this file for runtime versions, application-workaround messages and DXGI latency/swapchain setup. Logging overhead still needs a matched control.

## Lightweight Minecraft pacing capture

Set `FGVK_PACING_PROFILE=1` in the game's existing launch environment and restart it. Keep its working graphics/profile setup. For Prism Launcher, preserve the current Wrapper Command and prefix it with `env FGVK_PACING_PROFILE=1`, for example `env FGVK_PACING_PROFILE=1 mangohud /absolute/path/to/fgvk`. The profiler records CPU boundary/phase timing without enabling the broader presentation diagnostics, health worker, new GPU queries, or per-frame writes. It works with other Vulkan games too.

The Renderer creates a private `fgvk-pacing-<uid>-<pid>-<timestamp>.log` under `${TMPDIR:-/tmp}` at swapchain creation and prints its path once. Only framegen-vulkan timing and process/profile identity records enter this file; arbitrary game/launcher output, Java arguments and account details are not captured. CPU/GPU-only capture retains up to 16 MiB and restarts with a `pacing-profile-log-wrap` marker when full. With `FGVK_PACING_PROFILE_WAYLAND=1`, the file instead preserves its beginning up to 64 MiB, emits `pacing-profile-capture-limit`, and stops writing; earlier FG/settings portions are never overwritten. The session header records `capture_limit_bytes` and `retention=stop|wrap`. Concurrent writers use a nonblocking lock; missing/partial records produce a `pacing-profile-capture-gap` marker. No collection worker is added. Find and filter the newest capture with:

```bash
~/.local/bin/fgvk-diagnostics --pacing --lines 5000 performance > /tmp/framegen-vulkan-pacing.txt
```

Use an explicit installed helper path if `fgvk-diagnostics` is not on PATH. `--log /absolute/path` selects an older capture instead. `FGVK_PACING_PROFILE_LOG=/absolute/new-capture.log` selects a new output file; existing files, symlinks, FIFOs and devices are refused. `FGVK_PACING_PROFILE_LOG=stderr` restores console-only output for launchers that retain it. Minecraft's `latest.log` and Prism's own launcher logs do not necessarily contain the native stderr stream.

From a source checkout, generate a readable timing and hitch report with:

```bash
python3 engine/scripts/analyze-pacing-profile.py /tmp/framegen-vulkan-pacing.txt --top 10
```

The report keeps process/context streams separate and rejects malformed or unsupported windows. Add `--skip-seconds 15` to exclude the first 15 seconds of recorded windows when comparing warmed gameplay. Do not silently omit loading when investigating startup hitches. Session, wrap and capture-gap records remain in the filtered capture for evidence review.

Current captures also retain `pacing-profile-output` version-1 records for individual lower-present attempts: `ordinal` and `source` identify the output and source batch; `generated`, `deferred` and `image_index` identify its role, delivery path and acquired image; `scheduled_ns`, `started_ns` and `finished_ns` retain its requested CPU deadline and actual call boundaries in the monotonic clock. A zero deadline means unavailable. Records are buffered with the existing one-second window, with at most 512 per window; `output_trace_dropped` makes overflow explicit and ordinal gaps prevent the reader from inventing intervals across missing samples. The report shows output-gap percentiles, individual worst pairs, preceding lower-call durations and deadline lateness, and separates changes in Smooth Cadence, cap and present mode. Image indices and roles identify submissions, not image pixels or visible frames. The final incomplete window remains unavailable.

For native Wayland games, including Wine Wayland, add `FGVK_PACING_PROFILE_WAYLAND=1` to the existing launch environment and restart with a build containing this observer. It implies CPU capture and does not enable GPU queries. The summary's `wsi=wayland|xcb|xlib|unknown` records the Vulkan surface entrypoint; `wayland_requested` and `wayland_observer` distinguish the requested capture from successful observer construction. XCB probe results do not qualify a Wine Wayland game. This observer uses the application's existing `wl_display` and `wl_surface`, a private event queue, and version 1 of the compositor's `wp_presentation` protocol. It does not open a second display, read the socket, dispatch application callbacks, issue commits, set presentation targets, or change Vulkan IDs/waits. The application's existing display reader supplies events; a reader that does not service this display can leave observations unavailable.

`pacing-profile-wayland` records retain feedback requests, actual lower-call boundaries/results, and the compositor's `presented` or `discarded` outcomes, correlated by process, surface token and feedback ID. Version 2 writes only fields applicable to each event, preserving request identity once and using `started_ns` for the actual lower-call entry. The reader supports both the older verbose version 1 and compact version 2 and joins terminal identities only to one matching request. Requests retain the framegen-vulkan context/source, image index and generated/real role. `presented_ns`, `sequence`, `refresh_ns`, `flags` and `output_id` come from presentation feedback; `clock_id` names the compositor's clock. `presentation_now_ns` samples that clock at the request, with `calibration_span_ns` bounding the local sampling interval. Do not subtract these timestamps from the host clock without a valid clock relationship. `received_ns` is when framegen-vulkan dispatches its queued callback, so callback delays are not presentation gaps. The reader keeps clocks/surfaces/outputs separate and reports compositor presentation-gap percentiles, discards, repeated timestamp/sequence observations and unavailable/pending evidence. Summary windows additionally retain configured FG enablement, multiplier, Adaptive state and configured cap separately from the effective cap, so FG transitions split report segments explicitly. Hardware-clock/completion flags describe the reliability of the compositor's report; they do not inspect image pixels or measure input latency.

Feedback attaches to the next surface commit after its request, which framegen-vulkan issues immediately before the lower present call. A driver that defers commits can associate multiple requests with one commit. Repeated timestamp/sequence observations therefore make distinct output-to-visible-frame assignment ambiguous; never label them independent visible frames or proof of repeated pixel contents. The observer retains at most 256 outstanding feedback proxies and 512 buffered records, publishing approximately once per second. Unavailable reasons distinguish pending discovery/clock events, absent protocol, capacity and proxy failures; `pacing-profile-wayland-gap` reports record overflow. Surface destruction abandons outstanding observations and releases only the observer's proxies/queue. Profiling costs include extra protocol requests and callback dispatch; compare the same game scene with the flag off/on before claiming negligible overhead. Remove the flag after capture. For a focused comparison, keep cap, cadence, resolution and camera motion fixed while recording FG off then on, and note which portion visibly stutters.

When lower calls are regular but compositor feedback is uneven, the source-checkout companion below captures the driver's actual Wayland buffer-attachment and commit requests without rebuilding or installing framegen-vulkan. Prefix the entire existing game launch command with `python3 /absolute/path/to/framegen-vulkan/engine/scripts/wayland_pacing_protocol.py --`; preserve existing launcher arguments and profile flags. For Steam, place that prefix before the existing framegen-vulkan command and `%command%`. For a terminal launch:

```bash
python3 /absolute/path/to/framegen-vulkan/engine/scripts/wayland_pacing_protocol.py -- ~/.local/bin/fgvk /path/to/game
```

The companion enables `WAYLAND_DEBUG=client` and `FGVK_PACING_PROFILE_WAYLAND=1` in its child only. It passes ordinary game stderr through, drops unselected Wayland traffic, and writes selected numeric/object-only presentation, attachment, commit and synchronization messages into a new mode-0600 `fgvk-wayland-protocol-<uid>-*.log` under the temporary directory. It preserves the beginning up to 64 MiB and stops with an explicit marker; `--output /absolute/new-file.log` selects a new file and existing paths are refused. It preserves child arguments, standard input/output, exit status and termination signals. It neither installs a library nor changes saved settings. Use it for a short focused run, then remove the launch prefix: Wayland's per-message stderr logging and the companion pipe can perturb timing. Launchers that discard or redirect the game's stderr can leave this companion empty; do not treat that as absence of commits.

Analyze both captures with `python3 engine/scripts/analyze-pacing-profile.py /path/to/fgvk-pacing.log --wayland-protocol /path/to/fgvk-wayland-protocol.log`. The matcher joins exact compositor clock/timestamp/sequence/refresh/flags/output identities to feedback-object lifetimes and their next `wl_surface.commit`, deduplicates multiple observers of one commit, and rejects missing/conflicting associations. It compares adjacent lower-call, commit-request and compositor-presentation intervals within their separate clocks; it never subtracts realtime protocol timestamps from monotonic CPU timestamps. Periodic realtime/monotonic calibration rejects interval comparisons if a clock step is detected. Conflicting object IDs from multiple unlabelled display/process streams make coverage partial. Commit timestamps mark client-side protocol marshalling, not socket delivery or compositor receipt; picture progression remains unmeasured. Retain both raw files together when this boundary is under investigation.

For unresolved picture progression, `FGVK_PACING_PROFILE_CONTENT=1` additionally arms a small image capture in supporting builds. It implies CPU profiling and currently supports Fixed 2x SDR without spatial scaling. The `pacing-profile-content state=armed` record prints a new private binary path and its `.trigger` path; no diagnostic GPU allocation or image readback occurs before that trigger exists. Warm the scene first, then create the named trigger as a regular file owned by the game user while panning consistently. The next eligible sources record up to 128 pairs of downsampled 192×108 RGBA8 real/generated images into a separate exclusive mode-0600 file (at most 21,268,480 bytes). These files contain game pictures; timing-only collection does not copy them automatically. Source/batch/backend-history ordinals, generated/real role, actual image index/handle, copy/caller/private-present queue identities, CPU recording time and CPU observation at the existing render-fence boundary accompany every picture. Recording uses existing source/generated copy command buffers; readback follows the existing completed-copy fence, without another submission, worker or GPU wait. The owner retains its small transfer image and staging buffer through ordinary swapchain retirement. Capturing adds GPU transfers, CPU readback and file I/O; it is diagnostic overhead and changes no saved setting or presentation deadline. The final unfinished batch can remain unavailable.

Inspect a captured image sequence with `python3 engine/scripts/analyze-frame-content.py /path/to/fgvk-content.bin --json /new/report.json --preview /new/sequence.gif`. Binary decoding uses Python's standard library; offline motion estimates require NumPy and the optional deliberately slowed GIF requires Pillow. The report preserves missing/partial records, refuses unsupported schemas and unbounded sizes, checks exact captured-picture duplicates only across adjacent source/backend-history steps, and estimates generated-frame progress between the previous and current real picture. Expected midpoint progress is approximately 0.5 during coherent translation; image registration is an estimate, not proof of temporal correctness for arbitrary motion or occlusion. The capture does not measure displayed pixels, physical scanout or input latency. Remove the content flag and protocol wrapper after diagnosis.

Both actual application present-wait APIs now record `application-present-wait` windows in this same lightweight capture, independently of broad diagnostics. They include waiter thread, swapchain, API, called ID range, successes, polls, timeouts, errors and total call duration, including any retained-ID handoff. These are actual calls, unlike `fifo_caller_timing_sources`. `wait_capture=1` identifies windows from a build with this coverage; absence from older captures is unavailable evidence. The report associates waits by process and swapchain within the captured context interval. Every collector preset retains the wait and individual-output records. Wait durations alone do not establish that the producer was blocked by the waiter.

The outer `application-queue-present` window separately records `deferred_join_samples`, `deferred_join_mean_ms` and `deferred_join_max_ms` for the device's retained-output drain before configuration polling. This wait is included in outer present duration and precedes the inner `layer_present` timer. The configuration-update metric excludes it. A large difference between outer and inner present times must not be attributed to game work or wait2 without this phase measurement. Older captures lack the join field; the reader reports it as unavailable. This observation does not change pacing or the drain's synchronization contract.

Version 2 records include the final Smooth Cadence state, effective source cap, lower present mode and swapchain handle in each window. Each primary metric reports sample count, minimum, mean, maximum and the number above 33⅓ ms. `source_interval` measures successive entries into framegen-vulkan's swapchain present; `layer_present` includes synchronous pacing and work there; `outside_layer` measures the gap from the previous return to the next entry, including game work, limiter sleeps and application acquisition. `output_interval`, `within_batch` and `between_batches` measure lower-present call starts, including attempted calls that fail; `lower_present` measures their CPU duration and `output_errors` counts negative Vulkan results. Tiny within-batch gaps alongside long between-batch gaps reveal clustered submissions.

`ready_batches` and `cap_batches` count planned output spacing. `worker_batches` counts completed retained batches, and `worker_readiness_misses` counts batches that exhausted readiness or failed it and drained images through ordinary semaphore-protected delivery. Planned counts alone do not establish actual submission spacing or physical cadence. Worker readiness runs outside the producer's `readiness_wait` timing; compare output intervals and GPU spans as well.

`source_cap_wait`, `readiness_wait` and `output_wait` separate measured cap sleeps, the native ready-batch timeline wait, and per-output sleeps. `planned_output_interval` records selected CPU output spacing. `output_wake_lateness` and `source_cap_wake_lateness` measure time beyond the later of the requested deadline or entry into the sleep; `source_deadline_lateness` also retains lateness when framegen-vulkan work already passed the cap deadline before the final sleep. Private phase means/maxima separate render-fence waits, scheduling, source copy, generated-image acquisition, generated submission, generated presentation, original presentation and unattributed work. `application-acquire` and `application-queue-present` records add application-boundary blocking and configuration-update windows without broad diagnostics.

`timing_driver_attempts`, `timing_application_attempts`, `timing_ext_attempts`, `timing_google_attempts` and `timing_bridge_attempts` count the timing path actually forwarded to lower presentation. Driver means no explicit Vulkan timing node or private bridge annotation from this call; CPU pacing can still apply. Application means a caller-supplied timing node, without reading or attributing its timestamps. EXT and Google mean framegen-vulkan attached a target; bridge identifies the separate protocol owner. These are attempts, including rejected lower presents, not completed or visible outputs. Deferred delivery records its timing path when admitted and its CPU output observation when joined; window counts can therefore differ. `present_target_interval` measures consecutive strictly increasing framegen-vulkan EXT/Google requests in the host clock, across window boundaries but never across a different or untimed path. `present_target_discontinuities` counts repeated/backwards requests without learning a positive interval. No extra Vulkan query is issued. These fields distinguish an inactive timing path from tightly submitted outputs with distinct targets; targets do not establish effective compositor scheduling, presentation completion or physical visibility. Older version-2 captures lack these optional fields, and the reader reports that evidence as unavailable. `fifo_caller_timing_sources` counts FIFO source batches whose device requested a timing extension or enabled presentation waits. It records capabilities, not whether the caller supplied a timing target or whether CPU pacing was excluded. The earlier synchronous FIFO candidate excluded these batches; the current synchronous fallback preserves caller IDs/waits without consuming their namespace and excludes actual timing nodes instead. Inspect ready-batch counts, ownership and readiness budgets separately.

The `worst_source_*` fields retain one correlated interval per window: the preceding framegen-vulkan present duration, its cap/readiness/output waits and private phases, time outside that present, and the profiler publication immediately after it. Those waits/phases are portions of the framegen-vulkan duration; do not add them again. `worst_source_profiler_publish_ms` is included in outside time. `profiler_publish` measures completed-window bookkeeping and formatting/writing cost, including long sink writes, in the following window. It excludes observation calls elsewhere in the frame. Empty metrics have zero samples. Storage remains constant across long sessions; the final incomplete window is not emitted.

Readiness/fence waits are CPU blocking, not GPU execution measurements. Outside time cannot distinguish Java/game work, garbage collection, scheduler preemption, driver acquisition and game limiting by itself. CPU output submissions do not establish physical visibility, dropped frames or input latency. Use independent JVM/GPU/compositor evidence when those boundaries remain uncertain. A wait's duration alone does not prove a pacing regression: intentional output sleeps can improve cadence. Qualify complete profiler overhead with paired game captures; a fast-sink CPU benchmark does not establish Minecraft or launcher overhead.

For opt-in in-game Frame Generation GPU cost, use `FGVK_PACING_PROFILE_GPU=1` instead of the CPU-only flag. It also enables the same CPU capture. In Prism, preserve the existing Wrapper Command and prefix it with `env FGVK_PACING_PROFILE_GPU=1`, for example `env FGVK_PACING_PROFILE_GPU=1 mangohud /absolute/path/to/fgvk`. Restart the game after changing this process-start flag. Default operation and `FGVK_PACING_PROFILE=1` alone allocate no GPU queries.

The GPU mode reuses the backend's timestamp-query profiler. A fresh Frame Generation context gets one bounded query pool; after the normal previous-work fence wait has established completion, the next backend schedule reads the previous batch before reusing its queries. No additional GPU wait, worker, device idle or blocking query-result flag is introduced. Samples arrive later than the CPU frame that submitted the batch, and the final uncollected batch is omitted. History-only work supplies no generated-batch sample. Duplicate scheduling retries cannot duplicate a collected batch, and a query-read failure disables automatic reads for that context while preserving ordinary generation. Missing/unsupported timestamp evidence remains unavailable, not zero cost.

GPU mode additionally makes one nonblocking `vkGetFenceStatus` observation of the existing final generated-copy fence after each applicable lower present returns. Individual output records set `copy_checked=1` and retain the unchanged `copy_status`: `0` is signaled, `1` is pending, and negative results retain errors. `copy_sampled_ns` timestamps the completed observation; the reader reports its delay/cost after lower return. `copy_checked=0` is unavailable evidence, including CPU-only capture and paths without that fence. This fence covers the final copy of the source batch, not each individual image, compositor consumption or scanout. Its state after return does not establish its state at call entry, and a pending final fence does not by itself prove that an earlier generated image was unready. The sampler neither waits for the fence nor changes output deadlines, results or pacing policy, and adds no GPU resource. Qualify it with synchronization validation and matched GPU-mode off/on captures.

`gpu_prepass`, `gpu_generation`, `gpu_output` and `gpu_span` retain sample counts and minimum/mean/maximum milliseconds for preprocessing, the sum of generated-output spans per batch, individual generated outputs and the complete backend batch respectively. Component spans are contained in the complete span; do not add them again. GPU spans can include queue scheduling/preemption gaps, and exclude Minecraft/game rendering, application-device source copies/scaling, compositor work and scanout. `gpu_readback` measures the CPU cost of collecting that batch, separately from its GPU time; the cost also remains inside the ordinary scheduling phase and must not be added to it again. The report reader prints weighted means and maxima, plus explicit unavailable evidence when no completed samples exist. These are aggregated backend timings, not an attribution of the CPU window's worst hitch or an input-latency measurement. Query writes/readback can perturb the run; compare matched CPU-only and GPU-enabled captures, then remove both flags for normal play.
