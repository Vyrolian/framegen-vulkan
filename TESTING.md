# Testing MAKO

MAKO separates deterministic product checks from real-hardware evidence. Portable tests are required for every change, but they do not prove Vulkan presentation, image quality, Gamescope behavior, or game compatibility.

## Ownership

| Boundary | Owner |
| --- | --- |
| Product code, portable tests, production-path CLI tools, package contracts, and Gym bridge | MAKO |
| Licensed-model execution, declarative hardware scenarios, Vulkan/Gamescope orchestration, runtime assertions, performance budgets, artifact validation, and sanitized local evidence | Private MAKO Gym |
| Comparative real-game sessions, schemas, checksums, and append-only evidence | Private MAKO Traces |

Portable MAKO tests must not require MAKO Gym, `Lossless.dll`, an AMD GPU, Gamescope, or a compositor. MAKO Gym consumes MAKO's public executable and diagnostic boundaries; it must not copy production C++, shaders, thresholds, or configuration owners.

[Ongoing maintenance](MAINTENANCE.md) maps upstream dependencies to their owners, update triggers and validation obligations. Record exact runtime/build identities with hardware evidence and keep them separate from build pins and source reviews. The [Gamescope compatibility record](engine/gamescope-compatibility.json) tracks supported protocol versions and scoped review/validation entries; an empty hardware list means no qualifying evidence has been entered there.

## Validation cycles

| Cycle | Proves | Does not prove |
| --- | --- | --- |
| Portable change gates | Deterministic Renderer, Decky, schema, package-policy, sanitizer, and producer behavior | Real Vulkan presentation, AMD image quality, or installation |
| Direct device iteration | A focused change works on the current development installation | Archive layout, clean-checkout reproducibility, 32-bit, or Flatpak behavior unless selected |
| Complete tester ZIP | Local source packages as one self-contained build | A clean pushed commit, real game behavior, or public asset |
| Local release-candidate check | The already-built complete ZIP matches the clean pushed commit and contains verified native and Flatpak payloads | GPU behavior, installation, or the published download |
| Manual release-candidate matrix | Selected games survive relevant presentation, focus, overlay, hitch, and recreation scenarios | Untested games and hardware |
| Published-package check | The exact GitHub host, Flatpak, and Arch assets match their recorded checksums and install through their user-facing paths | Universal compatibility |

Use [MAKO Decky packaging](plugin/docs/PACKAGING.md) for development and tester builds and [How to release MAKO](HOW_TO_RELEASE.md) for release validation and publication.

## Portable gates

The `Tests` workflow runs on every pull request and push to `main`:

- MAKO Decky backend/frontend tests, type checking, coverage, generated-contract freshness, localization, production bundling, and package-license contracts;
- MAKO Renderer CTest with GCC and Clang using the [native package Vulkan-Headers revision](engine/vulkan-headers-revision.txt) and its required-header check, including Qt, localization, synthetic model inspection, launch policy, generated-SPIR-V freshness, shared Flatpak-header module freshness/mutation checks, and the pinned vkBasalt release/generated-module contract;
- the Arch package release-pin, alternative-package identity, non-mutating lifecycle-hook, automated release-sync, and exact-release build-wrapper contracts;
- portable Renderer policy tests under ASan and UBSan using the same pinned Vulkan headers as the native package;
- protected-input, trace-producer, and local release-candidate contracts on their supported hosts; and
- Markdown formatting.

The owning component tests remain authoritative for their detailed invariants.

It covers the nonzero `disabled` status from SteamOS, preservation/restoration of the initial read-only state, transaction/restoration failures, and rejection of invalid status results before mutation. Actual GPU sampling, real in-game hotkeys/control behavior, the optional tkinter window, layer activation, frame-counter position and logging overhead require separate hardware evidence; the tool does not measure physical input latency or FG-only GPU milliseconds. See the [capture workflow](engine/docs/COLLECT_DIAGNOSTICS.md#compare-mako-and-nvidia-smooth-motion-without-nsight).

For diagnostic changes, `runtime-overhead --diagnostics-overhead` compares logging off/on while keeping Frame Generation active, rather than comparing FG off/on. It reuses the canonical cases and production workload, balanced pair order, portable health validator, exact allocation checks, and hardware identity guard. MAKO Gym is an optional sibling checkout for targeted hardware work. The bridge skips clearly when Gym is absent unless `--require` is used; required mode also rejects a missing runner or incompatible `GYM_CONTRACT_VERSION`.

Gym contract version 19 adds the `pacing` suite for explicit Gamescope VRR feedback, pacing-owner transitions, and independent compositor-completion evidence while retaining defined-content benchmark inputs, performance baseline schema 4, and explicit CLI precision selection. Use a matching Gym checkout; older runners must not silently omit VRR pacing coverage or reinterpret an FP32 workload through the CLI default.

Before any hardware run, validate Gym's portable contracts with `(cd ../MAKO-Gym && ./scripts/check.sh)` or `just check` from its checkout.

The bridge exposes one selection pattern. `--list-suites` discovers suites, `--all-suites --validate` validates their inventories without hardware, `--suite NAME --list` discovers rows, and `--filter REGEX` runs a subset. Omitting `--filter` runs the complete selected suite:

```bash
./engine/scripts/run-mako-gym.sh --list-suites
./engine/scripts/run-mako-gym.sh --require --all-suites --validate
./engine/scripts/run-mako-gym.sh --suite recovery --list
./engine/scripts/run-mako-gym.sh --suite recovery
```

Run the smallest suite and filter that can observe a change. When claiming complete hardware qualification for a selected boundary, include Gym's bounded `constraints` suite with the relevant candidate CLI and launcher; Gym's compact hardware runner applies its own case mapping. A filtered pass is evidence only for its selected rows. Widen to the complete affected suite when a shared production owner changes. A release does not automatically select every suite; run all suites only for a genuinely cross-cutting change or an explicit maintainer request.

Retained evidence may be reused when the exact Renderer/package identity and source commit, host and driver, Gym commit, configuration, and relevant rows match the candidate. Record the prior run identifier. A code, package, driver, scenario, or assertion change invalidates the affected evidence.

## Native Fixed output handoff validation

Released-source tests additionally model queued bursts whose median differs from throughput, slower/faster workload transitions, long pauses and return to ordinary source qualification. Worker regressions cover overlap acquisition returning the first available image while later batches remain pending, zero-time queue-lock contention, finite/infinite budgets and lower acquire/present errors. Worker-copy pressure tests require readiness/expedite/output-limit skips to consume staged work and signal the continuation/fence exactly once without acquiring a generated image. A join after generated delivery must preserve its trailing real slot. Run these cases in full Renderer CTest, repeated `deferred-present` runs and the portable sanitizer lane; hardware checks must distinguish real-frame throughput, generated skips and physical cadence.

The `deferred-present` portable test covers native Fixed's bounded output-batch worker: value-owned singleton inputs, caller IDs/ID2, modes and fences, rejection of unsupported or duplicate nodes and borrowed result arrays, latest-ID serialized-wait detection with poll/older-ID/asynchronous controls, one presentation queue across complete generated/real/next-batch sequences and synchronous unsupported-chain/native fallbacks, one-source-batch admission and sealing, capacity/error/empty drains, per-output completion timestamps, no catch-up after delayed calls, poll/finite/infinite completion, actual recreation errors, repeated reuse, shared private-queue serialization, spare-image polling before the output deadline, nonblocking lock contention and joining at teardown. Private queue reservation preserves application indices and priority arrays, rejects protected-only requests and counts protected/ordinary requests together against physical capacity. Run it in full CTest and the sanitizer portable-policy lane. The presentation-policy detached-output regression also covers early/late source jitter runs of two, four, six and sixteen intervals with short acquisition joins without qualification holes, bidirectional median updates across workload changes and recovery with actual detached-slot acquisition feedback, including an 8 ms readiness cost that conceals a smaller sustained improvement. Additional presentation-policy regressions feed readiness timeouts back into detached cadence, retain full output spacing and unchanged source-cap deadlines after late native Fixed preparation, require actual detached evidence before a short cap-miss fallback, and release detached cap ownership when a slower game limiter takes over. The loaded-readiness regression feeds 2x–5x source arrivals through GPU readiness longer than one output slot, overlaps the bounded trailing output slots with next-frame work without accumulating a whole source interval of debt. Hardware evidence additionally needs pending application GPU work at present entry, actual source CPU work overlapped with output pacing, acquisition timing, idle/recreation, and validation-layer synchronization; a source limiter alone does not establish throughput recovery.

The `deferred-present` completion-wait regression calls both ID namespaces from another thread while the real output is retained. It requires zero-time and exhausted finite waits to avoid forwarding an unsubmitted ID, subtracts handoff time from finite driver waits, preserves infinite waits and driver results, propagates a rejected lower present, checks registry removal at teardown, and distinguishes a producer gated by completion from an acquisition overlapped with the wait. The source-pacing regression feeds 240 such gated intervals without inflating the previously qualified output period and checks that two slower completion-gated sources release the conflicting ready-output owner. Native wait2 validation must enable the ID2 and wait2 swapchain flags and exercise actual asynchronous waits with one and multiple outstanding source frames. Enabled features without wait calls do not cover this boundary; a good source FPS graph does not excuse an unassociated lower ID.

The detached ready-batch phase regressions additionally check every generated/real/batch boundary under alternating GPU readiness, late worker delivery and an inactive configured cap. Producer feedback covers relative and absolute limits, faster and slower work, all Fixed multipliers and acquisition joins; first-output deadlines run on the existing worker. Worker tests admit exactly one complete five-image batch and reject a sixth image or a second source batch. Hardware checks must still establish physical cadence and game motion independently of flat source graphs.
